# vnc-021 Acceptance Criteria Map

| AC-ID | Description | Verification Method | Verification Detail | Status |
|-------|-------------|--------------------|--------------------|--------|
| AC-01 | Server starts an HTTPS listener on the configured content port (default 8443) when `[http] enabled = true` | test | Integration test: start server with HTTP enabled, verify TCP connection accepted on configured port |
| AC-02 | Bearer token file generated at `{data_volume}/token` on first run (32 bytes, hex-encoded, mode 0600); printed to stdout once with `[UNIMATRIX TOKEN]` label | test | Integration test: start with no token file, verify file created (64 hex chars), permissions 0600, stdout contains `[UNIMATRIX TOKEN]` |
| AC-03 | Bearer token loaded silently from existing token file on subsequent starts | test | Integration test: create token file, start server, verify no token stdout output; verify server accepts pre-existing token |
| AC-04 | HTTP requests without `Authorization: Bearer <token>` header receive HTTP 401 | test | Integration test: send request without auth header, assert HTTP 401 with JSON error body `{"error": "missing or invalid authorization"}` |
| AC-05 | HTTP requests with incorrect bearer token receive HTTP 401; comparison uses `subtle::ConstantTimeEq` | test + grep | Integration test: send request with wrong token, assert 401. Grep: verify `ct_eq` usage in `src/http/auth.rs` |
| AC-06 | HTTP requests with valid bearer token reach MCP tool dispatch; tools execute identically to UDS/stdio path | test | Integration test: send authenticated MCP tool call (e.g., `context_status`) via HTTP, verify successful JSON-RPC response |
| AC-07 | `credential_type` in audit_log is `"static_token"` for HTTP-authenticated requests | test | Integration test: execute tool via HTTP, query audit_log, assert `credential_type = 'static_token'` |
| AC-08 | `agent_attribution` in audit_log is populated from `clientInfo.name` (MCP initialize handshake) for HTTP sessions | test | Integration test: connect via HTTP with MCP initialize including `clientInfo.name`, execute tool, verify `agent_attribution` in audit_log |
| AC-09 | TLS termination via rustls when `[tls] cert_path` and `key_path` are configured | test | Integration test: start with self-signed cert+key, connect with TLS client, verify handshake and tool execution |
| AC-10 | `tls.enabled = false` binds plain HTTP (no TLS) for proxy-terminated deployments | test | Integration test: start with `tls.enabled = false`, connect with plain HTTP, verify tool execution |
| AC-11 | Server refuses to start when `tls.enabled = true` but cert_path or key_path is missing or invalid | test | Unit test: attempt startup with `tls.enabled = true` and missing/invalid cert, assert descriptive error |
| AC-12 | HTTP listener uses a path-dispatching tower service; routes: `/health`, `/observe` (stub), `/*` (MCP) | test | Integration test: send requests to each path, verify correct routing (200, 501, MCP response) |
| AC-13 | `GET /health` returns JSON `{"version": "<semver>", "schema_version": <int>}` without authentication | test | Integration test: GET /health without auth, assert HTTP 200 with correct JSON; verify version matches crate version |
| AC-14 | `POST /observe` returns HTTP 501 with JSON `{"error": "Remote telemetry not yet implemented. See W2-7."}`. Bearer token auth required | test | Integration test: POST /observe without auth returns 401; POST /observe with auth returns 501 with exact JSON body |
| AC-15 | `/observe` registered in ProjectRouter routing tree for W2-6 multi-project path-prefix compatibility | grep | Grep: verify `/observe` appears in ProjectRouter route registration in `src/http/router.rs`, not as a pre-router intercept |
| AC-16 | Existing UDS/stdio transport paths are unaffected (zero regression) | test | Full existing test suite passes with no modifications to existing tests (`cargo test`) |
| AC-17 | `serve --foreground` mode (container) activates HTTP listener alongside UDS | test | Integration test: start in foreground mode with HTTP enabled, verify both UDS and HTTP connections accepted |
| AC-18 | `serve --daemon` mode activates HTTP listener alongside UDS | test | Integration test: start in daemon mode with HTTP enabled, verify both UDS and HTTP connections accepted |
| AC-19 | ProjectRouter struct exists with single-project default; requests route through it | test + grep | Integration test: verify HTTP MCP requests flow through ProjectRouter. Grep: verify `ProjectRouter` struct in `src/http/router.rs` |
| AC-20 | Config sections `[http]` and `[tls]` parsed from config.toml; `[http] enabled` defaults to `false`; `tls.enabled` defaults to `true` when both cert/key present, `false` otherwise | test | Unit tests: parse config with various `[http]`/`[tls]` combinations, verify all defaults |
| AC-21 | Maximum request body size enforced (1 MB); connection timeout enforced (30s) | test | Integration test: send >1MB body, assert HTTP 413; hold idle connection, verify disconnect after 30s |
| AC-22 | Maximum concurrent HTTP sessions enforced (configurable, default 32) | test | Integration test: open 32 connections, verify 33rd rejected/queued; verify configurable via `[http] max_connections` |
| AC-23 | Client setup docs for Claude Code, Codex CLI, and Gemini CLI covering MCP connection and hook configuration | file-check + manual | File check: `docs/client-setup.md` exists with sections for all three clients. Manual: review covers connection URL, bearer token, hook setup |
| AC-24 | All three clients use curl-based shell hooks — no local `unimatrix` binary required, no native HTTP hook handler | grep | Grep: hook examples in `docs/client-setup.md` use `curl` commands; no references to local binary or native handler |
| AC-25 | Claude Code docs specify `claude mcp add -H` workaround for #28293 | grep | Grep: `docs/client-setup.md` contains `-H` flag usage and references upstream bug #28293 |
