# nan-019 — Standing Release Gate: docker build → boot → register → per-slug-write smoke

> **NFR-maintenance feature.** Advances NFR capability **N5** ("the shipped artifact is always deployable as released") and guards **N3** ("writes are integrity-protected — never mis-routed across projects"). See `product/goals/personal-cloud/CAPABILITIES.md` (and the live `capability` corpus, entries #5161/#5163). This feature does NOT add new behavior to the shipped artifact — it makes an existing quality property *stay* true by wiring an already-built smoke (`docker-http-posture-smoke.sh`, from #786) into the release pipeline as a required, verify-by-name gate. Scoped 2026-06-19.

## Problem Statement

Releases ship the GHCR container image (`build-container-x64` / `build-container-arm64` → `create-container-manifest` in `.github/workflows/release.yml`), but **nothing in the pipeline exercises the actual shipped image end-to-end the way an operator would.** Unit and integration tests validate code pieces in isolation; no automated step builds the released image, boots it, registers a project, writes into it over the served HTTPS route, and confirms the write landed in the **per-slug** store rather than the path-hash store. An image can therefore pass every test and still be broken on first run for a real operator.

This is not hypothetical — it is the root of a whole class of shipped bugs:
- **#774** — remote clients couldn't connect (host-allowlist never wired into the shipped artifact).
- **#783** — a clean `docker run` of the GHCR image booted HTTP-off (because `UNIMATRIX_HTTP_ENABLED=true` lived only in `docker-compose.yml`, which the release does not ship) and silently mis-routed writes to the path-hash store instead of the per-slug store.

Both shipped green because **no test ran the real artifact's first-run path.** As the #786 uni-zero review put it, #783/#774/#769 and vnc-039's init wiring were all "the same blind spot: the shipped image's first-run path was never validated against the actual artifact."

The fix for the *class* already exists: `product/test/infra-001/scripts/docker-http-posture-smoke.sh` (built in #786) does exactly the build → boot → register → restart → per-slug HTTPS write → assert-landed sequence, and ran 3/3 locally. **The gap is that it is not wired as a standing gate** — it runs only when a human remembers. #786 explicitly deferred "wire the docker smoke into a Docker-capable CI lane," and the merge gate from the product lens was conditioned on that wiring being tracked (this feature).

There is a second, subtler failure mode this feature must close: the smoke **self-skips** when Docker is unavailable (`exit 3`). If wired naively, a runner without Docker would make the smoke skip and the job pass green — re-creating the false-green class (lessons #4796/#4970): an AC asserted as "passed" when it never actually executed. The gate must therefore verify the smoke **actually ran**, not merely that the job exited 0.

## Goals

1. **The shipped image is exercised end-to-end on every release — on BOTH arches.** Every release runs `docker-http-posture-smoke.sh` in a Docker-capable CI/release lane, against the real **pushed** image, performing reuse-pushed-bytes → boot-HTTP-on → register slug → restart → per-slug HTTPS write → assert the write lands in the per-slug store (`/data/.unimatrix/<slug>/unimatrix.db`), not the hash store, **and assert the per-slug store grew while the hash store did not (AC-05)**. The smoke runs against **both** the amd64 image (on `ubuntu-22.04`) and the arm64 image (on `ubuntu-22.04-arm`) — the shipped artifact is a multi-arch manifest, so never exercising arm64 would ship its first-run path unvalidated. First-boot embedding-model loading (#767) is plausibly arch-sensitive, exactly what single-arch coverage would miss.
2. **A smoke failure blocks the release.** If the image won't boot HTTP-on, or the per-slug route isn't live, or the per-slug write doesn't land in the per-slug store, the release is blocked — not merely logged.
3. **A skip is a hard failure, not a silent green (verify-by-name + positive run-marker).** If the smoke self-skips because Docker is absent (`exit 3`), the lane fails loudly. Beyond rejecting the skip, the gate asserts a **positive run-marker** — the smoke provably emitted its terminal success line (`ALL GATES PASSED`) — so a future early-exit-0 cannot masquerade as success. A green job must mean "the smoke ran to its end and passed," never "the smoke didn't run" or "the smoke exited 0 early." This closes the #4796/#4970 false-green class.
4. **Container-lane independence is preserved (ADR-004).** Wiring the gate does not couple the container/smoke branch to the binary/npm release branch: ARM64 runner flakiness or a smoke failure must not block (or be blocked by) the binary/npm jobs, and `create-release` must remain independent of the smoke per ADR-004.
5. **No silent retry.** The deployability gate has NO `|| retry` papering over Docker/network flake — a flaky deployability gate is itself a signal, and silently retrying undermines the integrity the gate measures.

## Non-Goals

- **No new deploy behavior or container changes.** This gate only *verifies* what already ships. It does not change the Dockerfile, the image's runtime posture, the served routes, or any first-boot behavior. (If the gate reveals a real artifact defect, fixing that defect is a *separate* feature/bugfix — the gate's job is to catch it, not to fix it.)
- **Not the functional per-slug analytics work (crt-056 / #787 = C5).** Orthogonal. This gate guards N3 (no mis-routed writes); crt-056 *extends* the per-slug surface N3 governs. They do not depend on each other.
- **Not a new smoke / not a rewrite of the smoke.** This feature *wires* the existing `docker-http-posture-smoke.sh`. The only smoke change in scope is the bounded, in-scope hardening in AC-05 (assert the per-slug DB grew, hash store did not). No new test scenarios, no new scripts.
- **Not a CI-lane (`ci.yml`, `pull_request`) gate.** The Rust/container validation has no home in the JS-only `ci.yml` matrix by design (per memory: GH CI is JS-client-only; Rust/container validation lives in the release workflow + protocol gates). The release workflow is the correct and intended home (it already builds the image). The trigger is the **release lane (tag `v*` push) PLUS `workflow_dispatch`** for human dry-run before cutting a release (e.g. after a release-config change) — but explicitly **NOT** `pull_request` (DECIDED, OQ-5).
- **No change to the binary/npm release jobs.** The gate is additive on the container branch only.
- **No new secrets.** The smoke is self-contained (it reads the bearer token and TLS cert out of the running container's data volume via a busybox sidecar). It needs no external credentials beyond what the image build already uses.

## Background Research (grounded in code/docs)

- **The smoke is complete and self-contained (`product/test/infra-001/scripts/docker-http-posture-smoke.sh`).** `set -euo pipefail`; builds `unimatrix:783-smoke` from the repo `Dockerfile` (or reuses a prebuilt tag via `IMAGE=`); asserts the runtime image ENV carries `UNIMATRIX_HTTP_ENABLED=true`; boots a clean `docker run` with NO http override; gates on the daemon log line `HTTP transport active` (and fails fast on the `set [http] enabled` hint = the #783 HTTP-off regression); registers slug `arch-research`; restarts to apply `[[projects]]`; POSTs a `SessionRegister` over the **cert-pinned** per-slug route `https://localhost:18443/v1/<slug>/observe` with the bearer (read from the volume), expecting `204`; asserts `/data/.unimatrix/<slug>/unimatrix.db` exists. All distroless-volume inspection is via a read-only `busybox` sidecar (never `docker exec` into the shell-less runtime image).
- **The skip contract is explicit and load-bearing.** Preflight `command -v docker && docker info`; on failure prints `SKIP: Docker not available` and **`exit 3`** — the script's own header says "Exits 3 (with a clear SKIP reason) when Docker is unavailable so CI flags it as a deferred step rather than false-green." So the exit codes are: **0 = ran+passed, 1 = ran+failed (`fail()`), 3 = self-skipped (Docker absent).** The gate's verify-by-name logic keys on these: only `0` may be green; `3` must be a hard failure.
- **GitHub-hosted `ubuntu-22.04` / `ubuntu-latest` / `ubuntu-22.04-arm` runners ship Docker preinstalled and running**, so in the normal case `docker info` succeeds and the smoke does NOT hit `exit 3` — the `exit 3` guard exists precisely to catch a *mis-provisioned or self-hosted* lane and refuse to pass it green. The gate must encode that intolerance, not rely on the runner always having Docker.
- **The release workflow already builds the image (`.github/workflows/release.yml:327-395`).** `build-container-x64` (ubuntu-22.04) and `build-container-arm64` (ubuntu-22.04-arm) each `docker buildx build --push` to GHCR with gha layer cache (`scope=container-amd64`/`container-arm64`). `create-container-manifest` (needs both) assembles the multi-arch manifest. This is the natural host for the gate — the image (or its build cache) already exists on these runners.
- **ADR-004 (entry #4572) keeps container jobs independent of binary/npm jobs.** "Container build jobs form a separate, independent branch… No `needs` dependency between container branch and binary/npm branch… `create-release` does not depend on container jobs." The gate must live on the container branch and preserve this independence (consequence: a smoke failure blocks the *container* release path / manifest, but not the binary/npm release — design must decide exactly where the block lands; see Open Questions).
- **The false-green class is a known, recorded lesson (#4796).** vnc-026 Gate 3c asserted a CI matrix as "passed" when it had never executed at that protocol stage. The takeaway — gates must not assert CI-dependent ACs as executed fact, and the delivery leader must watch the FIRST full GH run post-merge to completion — applies directly here: this gate runs on **tag push** (release), so its first real execution is post-merge, and platform/runner surprises are in-scope rework to watch for.
- **Local protocol gates are Linux-only; the GH matrix is the cross-platform gate (memory: `local-gates-linux-only-ci-is-crossplatform`).** This smoke is Linux/Docker-shaped and belongs in the release lane, consistent with that division. Budget a post-tag CI round-trip to confirm the gate actually runs green on the hosted runner (it cannot be proven by local Linux validation alone).
- **The #786 review's non-blocking hardening note.** uni-zero suggested also asserting the per-slug store actually **grew** from the write (and the hash store did **not**), to pin the data-landing assertion to the *literal* #783 symptom ("slug dir empty, hash dir populated") against a future *different-mechanism* regression. Gate 2's `204` already proves the route is live; Gate 3 only proves the per-slug DB *file exists* (register creates it). The grew-assertion is incremental and bounded — included here as an optional AC, not a separate feature.

## Proposed Approach

High-level, for the design phase to refine (not lock here):

1. **Add per-arch smoke jobs (`smoke-amd64`, `smoke-arm64`) to the container branch of `release.yml`**, on `ubuntu-22.04` and `ubuntu-22.04-arm` respectively. Each runs `bash product/test/infra-001/scripts/docker-http-posture-smoke.sh`. Triggers: tag `v*` push **and** `workflow_dispatch` (human dry-run).
2. **Test the PUSHED bytes, not a rebuild.** Each smoke passes `IMAGE=ghcr.io/<owner>/unimatrix:<tag>-<arch>` (after `docker login` to GHCR) so it tests the **exact pushed per-arch artifact**, not a self-build. The premise is "the shipped image misbehaves on first run"; a self-build tests a rebuild, which is definitionally not what ships. The smoke already supports `IMAGE=`. Self-build is **rejected**, not a design option (DECIDED, OQ-2). This orders each smoke *after* its per-arch push (`needs: [build-container-x64]` / `[build-container-arm64]`); the per-arch `:<tag>-amd64`/`-arm64` intermediates are briefly public, but the multi-arch manifest operators actually pull is never released until both smokes pass (see step 4).
3. **Encode verify-by-name skip-is-failure + positive run-marker.** Capture the smoke's exit code and treat **only `0`** as success: `3` (self-skip) and `1` (fail) both fail the job loudly ("smoke SKIPPED — Docker-capable lane is mis-provisioned; this is a hard failure, not a deferred step"). Do NOT let `exit 3` pass green. **Additionally assert the positive run-marker** — the smoke's terminal `ALL GATES PASSED` line was emitted — so a future early-exit-0 cannot masquerade as success.
4. **Gate the MANIFEST (human-preferred resolution of OQ-1; architect owns final mechanics).** `create-container-manifest` gains `needs: [smoke-amd64, smoke-arm64]`. The manifest is the tag operators pull, so gating it means no released artifact is ever un-smoked; both per-arch smokes feed one gate; per-arch intermediates being briefly-public is acceptable. This introduces NO `needs` edge from the binary/npm branch to the container branch (ADR-004 intact — the binary/npm branch gains no edge).
5. **AC-05 (in scope) — tighten the smoke** to assert the per-slug DB *grew* from the write and the hash store did *not* — pinning the data-landing assertion to the literal #783 symptom. Without it, Gate 3 only proves the per-slug DB file *exists* (register creates it anyway), so a future different-mechanism mis-route could write to the hash store and still pass. One bounded change, behind the same busybox-sidecar inspection pattern already in the script.
6. **No silent retry (DECIDED, OQ-6).** No `|| retry` on the smoke — a flaky deployability gate is itself a signal.

Rationale: testing the **pushed artifact** (not a fresh local build) is what actually closes the class — the bug is "the shipped image misbehaves on first run," so the gate must run the shipped image. Smoking **both arches** is incremental (the arm64 image is already built by `build-container-arm64`; smoking it is a job on an existing artifact, not a second build) and closes the arm64 blind spot #783 left open. The verify-by-name skip-is-failure rule plus the positive run-marker is the non-negotiable core: a gate that can silently skip — or silently early-exit-0 — is worse than no gate, because it manufactures false confidence (the #4796 class). ADR-004 independence is preserved so this regression guard cannot itself become a release-blocking flake on the unrelated binary path.

## Acceptance Criteria

- **AC-01:** On a release (tag `v*` push) **and on `workflow_dispatch`**, Docker-capable lanes run `docker-http-posture-smoke.sh` against the shipped image on **both arches** — `smoke-amd64` (`ubuntu-22.04`) and `smoke-arm64` (`ubuntu-22.04-arm`) — each executing reuse-pushed-bytes → boot-HTTP-on → register slug → restart → per-slug HTTPS write → assert-landed. Both jobs are part of the container branch of `release.yml`. The smoke is run against arm64 as well as amd64 — single-arch coverage is not sufficient for N5.
- **AC-02:** A smoke **failure** on **either arch** (smoke `exit 1`: image boots HTTP-off, per-slug route not live / not `204`, or per-slug store assertion fails) **fails the job and blocks the container release** (the multi-arch manifest is not released).
- **AC-03 (verify-by-name / skip-is-failure / positive run-marker):** A smoke **self-skip** (`exit 3`, Docker absent) is a **hard job failure with a clear diagnostic**, never a silent green. **Additionally, the gate asserts a positive run-marker — the smoke emitted its terminal `ALL GATES PASSED` line** — so a future early-exit-0 cannot masquerade as success. A green job provably means the smoke ran to its end and its behavioral assertions passed — not that it was skipped or exited 0 early. (Closes the #4796/#4970 false-green class.)
- **AC-04 (ADR-004 independence):** Wiring the gate introduces NO `needs` coupling between the container/smoke branch and the binary/npm branch. The binary/npm jobs and `create-release` are neither blocked by, nor able to block, the smoke. A smoke failure blocks only the container release path (the manifest).
- **AC-05 (in scope — required):** The smoke additionally asserts the per-slug store **grew** as a result of the write (and the hash store did **not** receive it), pinning the assertion to the literal #783 symptom ("slug dir empty, hash dir populated"). This is a required AC of this feature, not a fast-follow — without it Gate 3 only proves the per-slug DB file *exists*, which register creates anyway. One bounded change using the existing busybox sidecar pattern.
- **AC-06:** The gate tests the **actual shipped artifact** — the GHCR-**pushed** per-arch image tags (`:<tag>-amd64` / `:<tag>-arm64`). **Self-build is rejected**: the gate tests the pushed bytes, full stop — a self-build tests a rebuild, which is not what ships. No duplicate full image build is introduced (the pushed image is reused).
- **AC-07:** The first real release run post-merge is watched to completion on the hosted runners (**both arches**), and the gate is confirmed to actually run green (per the #4796 lesson — CI-dependent assertions are "configured + verified locally; GH execution confirmed post-tag," not asserted before execution).

## Constraints

- **Verify-by-name + positive run-marker, not by green suite (cross-cutting).** A job exiting 0 is NOT proof the smoke ran to completion. The gate must key on the smoke's distinct exit codes (`0` pass / `1` fail / `3` skip), must treat `3` as failure, **and must assert the positive run-marker — the terminal `ALL GATES PASSED` line — was emitted** so an early-exit-0 cannot masquerade as success. This is the load-bearing constraint — getting it wrong re-creates the exact false-green class this feature exists to kill.
- **Arch coverage must be named — no silent caps (HARD RULE).** N5's `done_when` and the gate's promise MUST NAME the arch coverage they actually have. A silent "amd64-only called N5-proven" outcome is FORBIDDEN. The decided path is **both arches smoked**. The only acceptable fallback (if arm64 is later deferred on cost) is: amd64 now + arm64 as a **NAMED, TRACKED fast-follow**, with N5 staying **PARTIAL** and the arm64 gap explicitly logged — never buried under a green checkmark. The preferred/decided path remains BOTH arches.
- **The gate tests the PUSHED bytes — self-build forbidden.** The smoke runs against the GHCR-pushed per-arch tags, never a rebuild on the smoke runner. A rebuild is definitionally not what ships. (DECIDED, OQ-2.)
- **No silent retry.** No `|| retry` on the smoke for transient Docker/network flake — a flaky deployability gate is itself a signal, and retrying undermines the integrity it measures. (DECIDED, OQ-6.)
- **Gate the manifest, not the per-arch pushes (human-preferred; architect owns mechanics).** The block lands on `create-container-manifest` (`needs: [smoke-amd64, smoke-arm64]`), so the released multi-arch tag is never un-smoked; the briefly-public per-arch intermediates are acceptable because operators pull the manifest, which is gated.
- **ADR-004 — container CI independence (entry #4572).** No `needs` edge between the container branch and the binary/npm branch; `create-release` stays independent of container/smoke jobs. The gate must not make ARM64/Docker flakiness able to block a binary/npm release.
- **Image-build duplication / runner cost.** The release already builds and pushes the image; the smoke should reuse it (`IMAGE=` + GHCR `docker login`) rather than rebuild from scratch. A full `docker build` of the ONNX-bearing image is slow; gratuitously doubling it is a cost the design should avoid.
- **Docker availability is the gate's whole point.** Hosted `ubuntu-*` runners ship Docker; the gate must NOT depend on that being eternally true — if a runner lacks Docker, the smoke self-skips and the gate must fail. Do not "tolerate" the skip.
- **Distroless runtime / busybox sidecar pattern.** Any AC-05 smoke change must keep using the read-only busybox sidecar for data-volume inspection — never `docker exec` into the shell-less runtime image. (Established in the existing script; cumulative test infra.)
- **No new secrets.** The smoke reads token/cert from the running container's volume; it needs only GHCR read (already available via `GITHUB_TOKEN` / `docker login`) to pull a pushed image. No external credentials.
- **Release runs on tag push → first execution is post-merge.** This gate cannot be proven by local Linux validation; budget a post-tag CI round-trip to confirm green (#4796 takeaway).
- **Test infrastructure is cumulative.** Wire the *existing* `infra-001` smoke; extend it (AC-05) rather than scaffolding a parallel script. Do not duplicate the smoke's logic in YAML.

## Open Questions

- **OQ-1 (architect-owned mechanics — human preference recorded) — Where exactly does the `needs` edge land to block the release without violating ADR-004?** The **architect decides the final mechanics**, but the **human-preferred resolution is recorded**: gate the **manifest** — `create-container-manifest` gains `needs: [smoke-amd64, smoke-arm64]`. The manifest is the tag operators pull, so gating it means no released artifact is ever un-smoked; per-arch intermediates being briefly-public is acceptable; both per-arch smokes feed one gate. ADR-004 is intact — the binary/npm branch gains no edge. The architect may refine the exact wiring but must honor: (i) the binary/npm branch stays uncoupled, (ii) no released multi-arch artifact is ever un-smoked.

### Decided (2026-06-19, human review)

- **OQ-2 — DECIDED: test the PUSHED bytes.** The premise is "the shipped image misbehaves on first run"; a self-build tests a rebuild, which is not what ships. AC-06 rejects self-build outright. The "briefly public before gate fails" worry is acceptable because the manifest is gated (OQ-1): per-arch `:<tag>-amd64`/`-arm64` intermediates are briefly public, but the multi-arch manifest operators pull is never released until both smokes pass. → AC-06, Constraints.
- **OQ-3 — DECIDED: smoke BOTH arches (amd64 + arm64).** The shipped artifact is a multi-arch manifest; never exercising arm64 ships its first-run path unvalidated (#783's blind spot narrowed to one arch, not closed). The arm64 image is already built (`build-container-arm64`), so smoking it is an incremental job on an existing artifact, not a second build. First-boot embedding-model loading (#767) is plausibly arch-sensitive. HARD RULE: arch coverage must be named — no silent "amd64-only called N5-proven". → Goal 1, AC-01, Constraints.
- **OQ-4 — DECIDED: fold in (in scope, required).** Without grew-assertion, Gate 3 only proves the slug DB file exists (register creates it anyway), so a future different-mechanism mis-route could write to the hash store and still pass (the literal #783 symptom). One bounded change using the existing busybox sidecar. AC-05 is now a required AC. → AC-05.
- **OQ-5 — DECIDED: release-lane (tag push) + `workflow_dispatch`, NOT `pull_request`.** `workflow_dispatch` enables a human dry-run before cutting a release (e.g. after a release-config change). `pull_request` is excluded. → Non-Goals, AC-01, Proposed Approach.
- **OQ-6 — DECIDED: no silent retry.** A flaky deployability gate is itself a signal; papering over Docker/network flake with `|| retry` undermines the integrity it measures. → Goal 5 (no silent retry), Constraints.
