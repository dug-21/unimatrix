# vnc-038 — Mandatory Project Identity at the Deployment Entrypoint (Revises the vnc-034 Contract)

> Revises the vnc-034 personal-cloud deployment contract. Triggered by bug #766: the headline attach flow `npx @dug-21/unimatrix init --bundle <bundle>` posts Ping/observe to `/v1/observe` and 404s. The decision (human-approved) is NOT to patch the 404 in isolation but to remove the no-slug / default-project deployment route entirely, make project identity uniform and frictionless at the entrypoint, and prove per-slug observe routing end-to-end. The spine is the **dumb-client invariant**: the server is the sole authority on route shape; the client composes no paths and posts to server-authored URLs verbatim. Scoped in a uni-zero session 2026-06-17.

## Problem Statement

The personal-cloud destination (goal #4934) advertises "one container, one bundle, one command." First end-to-end dogfood found that command is non-functional, and the root cause is structural, not a typo.

**The 404 (#766).** The no-slug client resolves `remote = base_url + "/v1"` (`packages/unimatrix/lib/init.js:307`) and the hook transport appends `/observe` (`packages/unimatrix/lib/hook-client/transport-http.js:84`), yielding `/v1/observe`. But `/observe` is a **top-level** route, split off before slug routing (`crates/unimatrix-server/src/http/router.rs:188`); `/v1/observe` reaches `parse_project_key`, where `observe` is treated as a candidate slug and rejected → 404 (`http/router/seam.rs:178-194`). The bundle path conflates the MCP base (`/v1/{slug|tools}`) with the observe base (root `/observe`).

**The root cause is client-side path composition.** #766 happened because the client built `/v1/observe` from its own grammar assumption — it composed a path the server never authored. This is the bug class to eliminate, not just the one route. ANY client-side path construction re-opens it. The invariant going forward: the server is the **sole authority on route shape**; the client composes no paths and derives no identity — it reads finished values from the validated bundle and posts to them verbatim. Route grammar is centralized server-side (one place, one test surface), so the client cannot produce a path the server did not author. This is consistent with architectural principle #6 — "the client is an adapter, not infrastructure."

**Why the route exists at all (the devex asymmetry).** Today the no-slug default is the *zero-step* path: the daemon auto-creates a path-hash store (ADR-004) and serves it via the `/v1/tools/...` default alias (ADR-005). Registering a real project slug is a *heavyweight, 3-step manual* operation: `unimatrix project register <slug>` creates the store but then explicitly prints "add to config.toml to enable routing: `[[projects]]` / slug = ..." (`crates/unimatrix-server/src/projects.rs:334-335`); the operator must hand-edit `config.toml`, then restart the daemon (the `[[projects]]` array is read once at boot to select `DefaultResolver` vs `MultiProjectRouter`, `main.rs:1004-1043`); only then does the client pass `--slug`. That asymmetry — zero-step default vs three-step real project — is *why* no-slug is the path everyone lands on, and why the headline flow exercises the broken `/v1/observe` route.

**The integrity stake.** vnc-034 established 1-client:1-project as a knowledge-integrity guarantee (C5): a client bound to project B that writes into project A's hash chain permanently and unrollbackably corrupts A. The no-slug default route is the one path where a bundle can silently land on the wrong/default store, because the slug is appended client-side (`init.js:303-308`) and is absent from the bundle entirely (`client_bundle.rs:58-68` — `{v, base_url, token, fp}`). Identity that is decided client-side, after the trust boundary, is the structural hole.

The fix is to make project identity **mandatory and uniform at the entrypoint**, carry the **server-composed endpoint URLs inside the bundle**, and make every request (MCP and observe) **provably route to exactly one project's store** via server-authored routes the client posts to verbatim — so #766 is closed by construction, not by rerouting.

## Goals

1. **Mandatory project identity at the entrypoint.** First boot comes up with NOTHING servable and a loud "register a project to begin" — there is no existing store to adopt (hard cut, no existing users to migrate). The first project is registered exactly like any other. The no-slug / default-project deployment route is removed: there is no longer a `/v1/tools/...` default alias that resolves a daemon path-hash store as a servable project. Every served request is under a known project identity. (This applies to the cloud/container served-project model; the local UDS install retains its path-hash identity per ADR-004 — see Non-Goals and AC-10.)

2. **Uniform, one-command project setup.** Every project — the 1st and the Nth — is added the IDENTICAL way: a single `register <slug>` command that creates the per-slug data dir AND writes routing intent (`[[projects]]`). The thing being eliminated is the **hand-edit-`config.toml` asymmetry** (zero-step default vs heavyweight Nth), not the restart. A restart to apply a newly registered project is acceptable for this single-dev, not-always-on deployment; the invariant is "same single command for project 1 and project N," restart-to-apply is fine. The `register`-then-hand-edit-then-restart sequence (`projects.rs:334-335`, `main.rs:1004`) is replaced by `register`-then-restart, with no manual config edit.

3. **Server-composed endpoint URLs travel in the client bundle.** The per-project bundle carries the **fully-formed endpoint URLs the server composed** — the project's MCP URL AND its observe URL — not a bare slug. A bare slug would still leave the client applying route grammar (the exact #766 failure spot); carrying finished URLs means the client substitutes nothing. The client reads identity *from* the validated bundle, so an attach cannot mis-target a wrong/default store. The bundle schema change is versioned (`v:2`) and strict-schema validated on both Rust and JS sides, with the parity corpus updated.

4. **Adding the "next" project is first-class and identical to the first.** Onboarding a 2nd/Nth project on a deployment is the SAME single `register <slug>` command as the first project — not a config-file edit. This is an overt objective, equal in standing to first-boot, not an afterthought.

5. **No cross-project pollination by design.** Every request — MCP *and* observe/telemetry — provably routes to exactly one project's store; mis-routing is structurally impossible, not merely validated. Observe is a server-owned per-slug route on the same per-request funnel as MCP; the client posts to the finished observe URL the bundle hands it and never decides where observe lives. This extends the vnc-034 C4 single-funnel guarantee (`http/router/seam.rs`) to the observe path, which today binds `resolve_store(Default)` once at boot (`main.rs:1048`) and is therefore single-store by construction.

6. **Root-cause guarantee for #766.** The design proves the observe HTTP path is reachable for the client end-to-end, per-slug: bundle → init → Ping/observe over the real route returns 200, for the project identity carried in the bundle. "Verify per-slug observe routing end-to-end (bundle → init → Ping/observe)" is an explicit acceptance concern, covering both the init-time validation Ping and runtime hook telemetry (the suspected wider blast radius in #766).

## Non-Goals

- **The sibling dogfood issues are NOT in scope** (see Dependencies). #767 (no embedding-model RW-mount on first boot) is a **separate usability prerequisite** for the dogfood — not absorbed into this diff. #768 (stale client-setup/README remote docs) is a **pre-committed fast-follow**: the hard cutover guarantees the attach docs go stale, so #768 is committed to ship right after, but is still a non-goal for THIS diff. #769 (healthcheck ERROR noise) remains separate.
- **No embedding-model provenance pinning.** The app already downloads the embedding model on first use, which satisfies "usable." The only gap is provenance (no hash pin); that is the right long-term direction but is deferred post-v1 — not a v1 concern, not part of this feature.
- **No RBAC / cross-project access control.** Isolation here is a concrete *routing* guarantee (each request resolves exactly one store), not an authz model. True N:N client↔project remains enterprise-only, additive on the C6 `BearerValidator` seam (vnc-034). This feature does not add per-slug authz.
- **No cross-project knowledge sharing / owner store** — unchanged from vnc-034; enterprise.
- **No monetization / tenancy model** — out of scope; OSS stays single-tenant, N projects.
- **No backward-compatible no-slug fallback.** This is a HARD CUTOVER (RD-1, RD-5) with no existing users to migrate. We do NOT keep a deprecated default route alongside the new one — keeping it would preserve the exact pollination hole this feature closes.
- **No new unauthenticated endpoints.** Any slug-discovery or self-registration surface stays behind the existing bearer auth; no new `/metrics`-style open surface (vnc-034 Non-Goal carried forward).
- **No local-UDS deployment-model change.** The "remove the no-slug default / retire `DefaultResolver`" decisions apply to the **cloud/container served-project model only**. The local single-project UDS install keeps its **direct path-hash store binding, untouched by the HTTP resolver** (ADR-004) — that is NOT a "no-slug default" and must NOT be forced to take a manual slug. Local STDIO/UDS opens its path-hash store directly at boot and threads the `Arc<Store>` straight to its handlers; it is NOT routed through the unified resolver. The unified resolver handles only `ProjectKey::Slug` (cloud); local bypasses it entirely. The local install is not being converted to a multi-project cloud, and SCOPE does not require local UDS to use a manually-supplied slug.

## Background Research (grounded in code)

- **The 404 is structural; the resolved fix combines server-routed observe + server-composed bundle endpoints (#766).** Of the original candidates — (a) client-only derive observe URL from `base_url`, (b) server-side route `/v1/{slug}/observe`, (c) bundle carries distinct mcp/observe endpoints — the resolved approach is **(b)+(c)**: observe is a server-owned per-slug route on the per-request funnel, and the bundle carries the fully-formed MCP and observe URLs the server composed. Candidate (a) is explicitly rejected because it keeps the client applying route grammar — the exact bug class #766 represents.
- **`/observe` is bound to one store at boot.** `main.rs:1048` resolves `resolve_store(&ProjectKey::Default)` ONCE at boot and threads that single handle into `ObserveContext`; `/observe` is deliberately NOT on the per-request MCP seam (ADR-005 / entry #4963). So today observe is structurally single-project — per-slug observe (objective 5) requires moving observe onto, or alongside, the per-request funnel.
- **The MCP funnel already exists and is per-request.** `SlugRouter` calls `resolve_store(parse_project_key(path))` once per request (`http/router/seam.rs:178-209`, entry #4963); the resolver is the sole Wave1↔Wave2 swap point (`DefaultResolver` vs `MultiProjectRouter`, `main.rs:1004-1043`). Removing the default alias means `parse_project_key`'s `/v1/tools/... -> Default` and the `_ => Default` backward-compat arm (`seam.rs:184,192`) must change, and `DefaultResolver` likely retires.
- **The bundle is cloud-wide, slug-free by design (ADR-001, entry #4954).** `{v, base_url, token, fp}`, version 1, strict 4-key schema, `unimatrix-bundle:<base64url(json)>`. The Rust side is the only encoder; JS decodes (parity corpus). The resolved change is a `v:2` bundle carrying the server-composed MCP and observe endpoint URLs (not a bare slug) + matched decoders + updated corpus. The strict-exact-key guard means a naive add breaks parity unless both sides move together.
- **Registration creates a store but not routing (`projects.rs`).** `register` (State C) creates `{base}/{slug}/` + genesis store, then merely prints config.toml instructions; it does NOT write routing intent. `[[projects]]` is the routing source of truth, read at boot (`configured_slugs`, `main.rs:1004`). The resolved approach (objective 2) has `register <slug>` **write the `[[projects]]` routing intent** instead of printing instructions (`projects.rs:334`), and a restart applies it via the existing boot-time read. No dynamic registry, no admin endpoint, no in-process reload — restart-to-apply is acceptable for this single-dev deployment. This significantly de-risks the feature: the prior "central build risk / live-reload mechanism" is no longer needed.
- **Reserved slugs.** `RESERVED_SLUGS = ["v1","health","observe","tools"]` (`config.rs:2483`). If `/v1/tools/...` ceases to be the default alias, `tools` may stop being reserved-for-shadowing; and a per-slug `/v1/{slug}/observe` route reshapes how `observe` is reserved. The reserved set is a downstream consequence of the route-grammar decision.
- **No store migration — hard cut, no existing users.** There is no legacy served store to migrate: the cloud/container model has no existing users, so first boot simply comes up with nothing servable and a loud "register a project to begin." No adopt/derive logic to design. (The local UDS path-hash store, ADR-004, is unaffected and keeps its own identity — it is not a served-project default.)

## Proposed Approach

High-level, for the design phase to refine (not lock here):

1. **Make identity mandatory at the route grammar (cloud/container).** Retire the `/v1/tools/... -> Default` alias, the `_ => Default` fallback, and `DefaultResolver`; every served cloud/container HTTP path carries a slug, resolved by a single resolver keyed by registered slugs (`ProjectKey::Slug` only). A single-project cloud deployment is just N=1 — one registered slug through the same resolver, no special-case arm. (Local UDS/STDIO keeps its **direct path-hash store binding, untouched by the HTTP resolver** — it opens its store directly at boot and is not routed through the unified resolver; no manual slug.)
2. **Carry server-composed endpoint URLs in the bundle (`v:2`).** The bundle carries the fully-formed MCP and observe URLs the server composed (not a bare slug), with matched Rust encoder / JS decoder and refreshed parity corpus. The client reads finished URLs from the validated bundle and posts to them verbatim — it composes no paths.
3. **`register <slug>` writes routing intent (`[[projects]]`); a restart applies it.** The same single command for project 1 and project N replaces register → hand-edit → restart with register → restart. No dynamic registry, admin endpoint, or in-process reload.
4. **Route observe per-slug, server-owned**, on the same per-request funnel as MCP, so init-Ping and runtime hooks resolve through one funnel and the client posts where the bundle tells it — closing #766 by construction (objective 5/6).
5. **Hard cut, no migration.** First boot serves nothing until a project is registered, failing loud with an actionable "register a project to begin." No existing served store to adopt or derive.

Rationale: the dumb-client invariant is the spine — centralizing route grammar server-side and handing the client finished URLs makes #766's bug class structurally impossible. Killing the hand-edit-`config.toml` asymmetry (uniform `register` for project 1 and N) means removing no-slug does not make devex worse. Restart-to-apply, acceptable for this single-dev deployment, removes the live-reload build risk entirely. The integrity guarantee (no pollination) is framed as a concrete routing property, not elevated to a vision goal (per prior guidance to avoid over-stating defensive structure).

## Acceptance Criteria

- **AC-01:** A deployment serves NO request under a default/no-slug identity. The `/v1/tools/...` default alias and the no-slug `/v1` client target no longer resolve a servable project; an attempt fails loud (no silent default-store landing).
- **AC-02:** Bringing up the first project is the single `register <slug>` command — it creates the per-slug data dir AND writes the `[[projects]]` routing intent, with no hand-edit of `config.toml`. A restart applies it (restart-to-apply is acceptable).
- **AC-03:** `register <slug>` writes routing intent rather than printing config instructions; after a restart the project is routable. The replaced sequence is register → hand-edit → restart, now register → restart.
- **AC-04:** Onboarding a 2nd/Nth project is the IDENTICAL single `register <slug>` command as AC-02/AC-03 — same command for project 1 and project N, with no config-file edit. (Restart-to-apply, same as the first project.)
- **AC-05:** The client bundle carries the server-composed MCP and observe endpoint URLs; the decoded, validated bundle yields finished URLs the client posts to verbatim, and the client composes no path and appends no slug after bundle validation. Bundle schema is versioned (`v:2`) and strict-schema rejects on both Rust and JS sides (parity corpus updated).
- **AC-06:** Given two registered projects, an MCP request and an observe/telemetry request each provably resolve to exactly one project's store; no code path lets a request bound to project B reach project A's store (single-funnel extended to observe).
- **AC-07:** End-to-end: bundle → `init --bundle` → init-time Ping/observe returns 200 over the real per-slug route (the #766 repro passes), for the identity carried in the bundle.
- **AC-08:** Runtime hook telemetry (every hook event) posts to a reachable per-slug observe route and is accepted (the #766 suspected wider blast radius is verified closed).
- **AC-09:** Hard cut (CLOUD/CONTAINER-HTTP only): a no-slug cloud/container HTTP deployment is no longer valid. First boot serves nothing until a project is registered, failing loud with an actionable "register a project to begin" message — no silent default. (No path-hash adoption logic: there is no existing served store to migrate.) This cutover applies ONLY to cloud/container HTTP deployments — of which there are currently zero; local STDIO/UDS users are explicitly unaffected and require NO data action (see AC-10).
- **AC-10:** The local single-project (UDS/STDIO / path-hash, ADR-004) install continues to function unchanged — it keeps its **direct path-hash store binding, untouched by the HTTP resolver**, and is NOT required to take a manual slug. The "remove the no-slug default" cutover does not apply to local UDS/STDIO. **Confirmed by code-cited impact analysis (GATE-2):** local STDIO (`main.rs:1158`) and UDS (`main.rs:859`) open `~/.unimatrix/{hash}/unimatrix.db` directly at boot and never touch `parse_project_key`, the HTTP resolver, `ProjectKey::Default`, or any bundle — so existing local stores keep working with NO migration and NO operator action, and delivery must NOT route local through the unified resolver (doing so would introduce the very cross-store regression this AC forbids).
- **AC-11 (#735 CI-1):** The first-boot bearer token is NOT emitted to stdout or logs (`http/token.rs:101` redacted/gated). The remote client obtains the token via the validated `v:2` client bundle, not stdout — consistent with the cloud HTTPS posture (NFR-06).
- **AC-12 (#735 CI-2):** After the route-grammar rewrite, `crates/unimatrix-server/src/http/router.rs` is at or under the 500-line guideline (extraction falls out of the rewrite).
- **AC-13 (#735 CI-3):** The stale module-level `#![allow(dead_code)]` and "until wiring lands" comment at `crates/unimatrix-server/src/http/public_url.rs:19` are removed.

## Constraints

- **Dumb-client invariant (cross-cutting).** The server is the sole authority on route shape. The client composes NO paths and derives NO identity — it reads finished values (the server-composed endpoint URLs) from the validated bundle and posts to them verbatim. Route grammar is centralized server-side (one place, one test surface); the client cannot produce a path the server did not author. #766 was caused by the client composing `/v1/observe` from its own grammar assumption — ANY client-side path construction re-opens that bug class. Consistent with architectural principle #6 ("the client is an adapter, not infrastructure").
- **Integrity is the basis, not access control** (vnc-034 C5): the 1-client:1-project boundary and no-pollination guarantee protect the unrollbackable hash chain. Framed as a routing guarantee, not a security/authz feature.
- **Strict bundle parity** (ADR-001): Rust is the sole encoder, JS decodes; any schema change is a versioned, dual-side, corpus-pinned change. The strict exact-key guard means partial rollout breaks decode.
- **A running daemon reads `[[projects]]` once at boot** (`main.rs:1004`); this is SATISFIED by restart-to-apply — `register <slug>` writes `[[projects]]` and a restart applies it via the existing boot-time read. No live-reload mechanism is built; restart-to-apply is acceptable for this single-dev, not-always-on deployment.
- **Distroless runtime has no shell** — first-boot/self-registration provisioning is done by the Rust binary, not a shell entrypoint.
- **Rust:** no `unsafe`, no `.unwrap()` in non-tooling code, max 500 lines/file, `tracing` logging, project error type with `.map_err` context.
- **No secrets in any DB** — token/cert stay as files on the data volume.
- **NFR-06 — cloud HTTPS posture / no token to stdout.** Under the cloud HTTPS posture, the bearer token must not be exposed on stdout or in logs (folded-in #735 CI-1). The token is delivered to the remote client only via the validated `v:2` bundle; the first-boot token print (`http/token.rs:101`) is redacted/gated (drives AC-11).
- **Reserved-slug set** (`config.rs:2483`) is coupled to the route grammar; changing the default alias forces a re-examination of what `tools`/`observe` reserve.
- **Test infrastructure is cumulative** — extend the existing bundle codec parity corpus, the seam/funnel tests, and project-lifecycle fixtures; do not scaffold isolated tests.
- **Hash chain is sacred** — `register <slug>` against an existing per-slug store must re-attach (open), never genesis-clobber (`projects.rs` State B precedent). (No path-hash migration path is in scope — hard cut, nothing to adopt.)

## Resolved Decisions

- **RD-1 (was OQ-1) — No store migration; first boot serves nothing. - **RD-2 (was OQ-2) — Bundle carries server-composed endpoint URLs (supersedes the earlier "single slug field" lean).** The `v:2` per-project bundle carries the fully-formed MCP URL AND observe URL the server composed, NOT a bare slug — a bare slug still leaves the client applying route grammar (the #766 failure spot).
