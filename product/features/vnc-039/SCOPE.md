# vnc-039 — Remote/Cloud `init` Wiring: a Pure-JS stdio→HTTPS MCP Bridge + Creds-File Hardening

> Restores the **on-demand `context_*` MCP surface over HTTPS** for cloud/remote-attached edge clients — the half of the personal-cloud contract that remote attach silently drops today. A remote-attached client gets the proactive/observation half (hook events posted to `observe_url`) but **zero `context_*` tools**: `initRemote()` explicitly skips `.mcp.json`. The decision is to wire `mcp_url` as a **stdio** MCP server in `.mcp.json` whose command is a NEW pure-JS bridge that owns its TLS, pins the bundle's `fp`, forwards the bearer token, and proxies stdio JSON-RPC ⇄ the cloud's Streamable-HTTP MCP endpoint. Plus an independent creds-file gitignore hardening (folded from #776). Scoped in a uni-zero session 2026-06-18. Closes #775 (and folds #776).

## Problem Statement

The personal-cloud destination (goal #4946) commits to a two-surface contract over HTTPS: proactive delivery (observe/inject) **and** explicit on-demand curation (`context_search`, `context_get`, `context_store`, …) — *"Multi-LLM connect identically via HTTPS with full intelligence-pipeline fidelity… retrieve knowledge on demand (search, lookup, get)."* Remote attach delivers only the first surface. The second is structurally absent.

**Evidence (client 0.8.1, `packages/unimatrix`):**
- `lib/init.js` `init()` routes any `--bundle`/`--remote`/`--token` to `initRemote()` (`init.js:524`). `initRemote()` writes hook events to `.claude/settings.json` and creds to `.claude/settings.local.json`, then **explicitly skips `.mcp.json`** (`init.js:450`: *"Skipped .mcp.json: remote mode does not register a local MCP server"*). `mcp_url` is persisted into `unimatrix.remote` (`writeRemoteSettingsLocal`, `init.js:230-237`) but **nothing consumes it as an MCP server** — it is dead config.
- `bin/unimatrix.js` routes `init` to the JS implementation and `execFileSync`s the **Rust binary** for every other subcommand (`unimatrix.js:54`). There is **no JS subcommand that speaks MCP-over-stdio to a remote** — a grep for mcp/stdio/bridge/proxy logic hits only `init.js` and `bundle.js`.
- The Rust binary is Linux-only and is the **server**; it cannot be the client-side bridge (the single-edge-language constraint commits non-Linux clients to pure JS). So the bridge MUST be new JS.
- The package has **zero runtime dependencies** (`package.json`: only `optionalDependencies` for the platform binaries). The entire hook client is built on Node stdlib (`http`, `https`, `net`, `crypto`). The bridge must follow the same posture.

**Why a stdio bridge, not a native `http`-type MCP entry.** Wiring `mcp_url` as a Claude-Code-native `http`/`streamable-http` MCP server makes Claude Code's own Node TLS verify the cloud's self-signed leaf — which it cannot trust (DEPTH_ZERO_SELF_SIGNED_CERT) and cannot pin to `fp`. This is the same wall `cert-pin.js` already documents (the F1 finding). The **house pattern** for daemon-backed MCP (entry #1897: local UDS daemon) is a thin stdio bridge — `.mcp.json` spawns a lightweight stdio process that proxies to the backend, so Claude Code sees a normal stdio server and never does TLS itself. The same trick solves remote: a JS stdio→HTTPS bridge that owns the TLS connection and pins `fp` via the existing `cert-pin.js` machinery. This subsumes the self-signed-cert problem and #773's env-HTTPS gap.

**Creds-file leak (folded from #776, INDEPENDENT).** `initRemote()` writes the cleartext bearer token to `.claude/settings.local.json` (`writeRemoteSettingsLocal`, mode 0600). That path is **neither gitignored nor tracked** — confirmed: the repo `.gitignore` covers only `.claude/worktrees/` and `.claude/scheduled_tasks.lock`, not `settings.local.json`. A single `git add -A` commits a live credential. Today `initRemote()` only **warns** when uncovered (`gitignoreWarning`, `init.js:273-297`) — it does not fix it.

## Goals

1. **Restore the `context_*` surface over HTTPS.** A **bundle-attached** (`v:2`) client gets a working `unimatrix` MCP server in `.mcp.json` that delivers the full `context_*` tool set over the cloud — at parity with what the local Rust-binary stdio server delivers locally. (Cloud MCP is bundle-only; the legacy `--remote` path is explicitly unsupported for MCP — OQ-2 resolved.)
2. **Pure-JS stdio→HTTPS MCP bridge.** Add a new bridge mode to the edge client: a Node-stdlib process that reads stdio JSON-RPC, owns a pinned TLS connection to `mcp_url`, forwards the bearer token, proxies to the cloud's Streamable-HTTP MCP endpoint, and writes responses back to stdout. No new runtime dependency; reuses `cert-pin.js`.
3. **`init` wires the bridge instead of skipping `.mcp.json`.** On the remote path, `initRemote()` writes a **stdio** `.mcp.json` entry invoking the bridge against the persisted `mcp_url`/token/`fp`, replacing the "Skipped .mcp.json" line. Idempotent and merge-preserving, mirroring the local `writeMcpJson` contract (`init.js:59-104`).
4. **Dumb-client invariant preserved.** The bridge posts to `mcp_url` **verbatim** — it composes no path, derives no slug, and appends nothing (the vnc-038 spine). `mcp_url` is the server-composed `.../v1/{slug}` Streamable-HTTP endpoint read from the validated `v:2` bundle.
5. **Credential leaves the repo working tree entirely, AND the file-mode remote observe break is fixed (folded #776).** The fix is **not** "gitignore `.claude/settings.local.json` on write" — it is to **stop storing unimatrix's credential in the repo working tree at all, and stop squatting Claude Code's own settings namespace.** The bearer token (plus `mcp_url`, `observe_url`, `fp`) moves to a **unimatrix-owned, out-of-tree path** under `~/.unimatrix/<projectHash>/` (mode 0600), keyed by **`projectHash`** (`sha256(projectRoot)[:16]`) — colocated in the existing per-project dir, one store per attached project (OQ-6 resolved). With the secret out of the working tree there is **no commit-leak vector left to gitignore against** — the hazard is removed at the root, not patched. Claude Code's `.claude/settings.json` keeps its hooks (Claude Code executes them and must find them there); `.claude/settings.local.json` is no longer written with the credential. Confirm the token is never echoed by `printSummary()` or any log on the remote path. **As a necessary part of this relocation**, reconcile the credential-resolution schema the hook client's file-mode `resolve()` reads: it must populate `config.pinnedFp` (today never set) and read `observe_url`+`fp` from the new store, so that **file-mode remote observe actually runs over pinned HTTPS** — a current break, not a latent one (today it silently falls through to UDS). Validated by AC-08d.

## Non-Goals

- **At-rest token encryption / OS keychain.** The bearer must remain recoverable in **cleartext at spawn time** — the bridge presents it as `Authorization: Bearer` on every request and bundle-attach is non-interactive, so at-rest encryption without an OS keychain/passphrase is theater (the key co-locates with the ciphertext). Cleartext-**at-rest** is therefore **accepted and unchanged**; keychain stays **enterprise-deferred** (per #775/#776). The bounded risk addressed here is **cleartext-in-the-repo** (accidental commit + namespace-squatting), not at-rest secrecy — and it is eliminated by relocation, not encryption.
- **A new MCP SDK / heavyweight dependency.** No `@modelcontextprotocol/sdk`, no bundling `mcp-remote` as a runtime dep. `mcp-remote` served only as a throwaway validation stand-in. The pure-JS-stdlib build is chosen **by decision** per the ass-080 (#777) build-vs-adopt finding — not merely the inherited zero-dep posture: adopting the only client SDK costs a 91-package / 25 MB / server-laden tree to obtain transport logic that must be *routed around* with a hand-written `node:https` fetch on the cert-pin path anyway, while importing the SDK's recurring server-transport CVE stream into a client-only bridge. Zero-dep is the deliberate, researched call.
- ~~**End-to-end validation of Scope A against a real cloud.**~~ **No longer a non-goal — #774 has merged (PR #778, commit 913b78cb, 2026-06-18):** rmcp now wires `allowed_hosts` from `UNIMATRIX_PUBLIC_URL`, so remote MCP requests no longer 403 at the host gate. **Live cloud end-to-end validation of the Scope A bridge IS now in scope for delivery** — it is expected, not deferred. Stub/local-endpoint validation remains a fast first tier (it needs no reachable cloud), but live validation against the cloud is now required, not gated-out.
- **Server-side changes.** vnc-038 already established the per-slug `.../v1/{slug}` Streamable-HTTP MCP route and the `v:2` bundle carrying `mcp_url`. The server side is ready (validated this session: a raw `initialize` POST with `Host: localhost` returns 200 + a valid MCP result). This feature is **client-only**; #774 (the host-allowlist wiring) was a separate server fix and has **merged** (PR #778, commit 913b78cb, 2026-06-18).
- **MCP over the legacy `--remote`/`--token` (env-HTTPS) path.** Cloud MCP is **bundle-only** (OQ-2 resolved → option c). The legacy path has no `fp` pin (#773); bridging it would write the bearer over an unverified TLS connection (a security regression), and adding MCP to legacy violates vnc-038's "keep legacy working, don't extend it." The legacy path stays as-is and emits a loud unsupported message for cloud MCP; #773 is resolved here by **deprecating env-HTTPS for cloud-attach**, not by adding a pin flag. **The legacy `--remote` user's path forward is to migrate to a `v:2` bundle — legacy is not "fixed" here.** Legacy credential relocation writes `fingerprint: null` and keeps legacy observe **unpinned** (unchanged behavior), and legacy gets **no** MCP bridge; both pinned observe and cloud MCP are bundle-only capabilities. This is the intended message (human-confirmed) and is consistent with deprecating env-HTTPS per #773 — the direction is bundle-only, not retrofitting the legacy path.
- **Rewriting the observe/hook transport POST mechanics.** This is a **narrow** non-goal — it does **not** mean "Scope B leaves the observe path untouched." Scope B **does** reconcile the credential-resolution schema the file-mode observe path reads (by necessity — see Correction below), and a Scope-B AC must validate that file-mode remote observe actually runs over pinned HTTPS post-fix. What it does **not** do is rewrite `transport-http.js`'s POST mechanics (the request/SSE/pinned-flush plumbing) — that machinery is correct and reused as-is. **Important correction to the prior framing:** file-mode remote observe does **not** in fact run over HTTPS today. The hook client's file-mode `resolve()` reads `unimatrix.remote.url` (which the writer never emits — it writes `mcp_url`/`observe_url`) and never reads `fingerprint`, so the path silently falls through to local UDS and would run **unpinned** if it didn't. Scope B fixes a **current break, not a latent one**: it must populate `config.pinnedFp` and repoint the file-mode resolve at `observe_url`+`fp` so remote observe runs over pinned HTTPS for real.
- **Auto-wiring for non-Claude-Code MCP clients (Codex/Gemini CLI) is DEFERRED.** The bridge itself is **client-agnostic** — any MCP client can spawn it as a stdio server (a real personal-cloud / multi-LLM win, goal #4946), and it is reusable across MCP clients by construction. But `init` auto-wires **only** `.mcp.json` (Claude Code). Generating config for other MCP clients is deferred — a conscious deferral, not an omission; the multi-LLM-connect personal-cloud criterion is advanced by the reusable bridge even though only Claude Code is auto-wired in this feature.
- **Changing the bundle schema.** The `v:2` bundle already carries `mcp_url`, `observe_url`, `token`, `fp` (entry #5081). No schema change.
- **`#768` stale remote-mode docs** — a separate pre-committed fast-follow (the new wiring makes the "skips .mcp.json" docs stale), not in this diff.

## Background Research (grounded in code)

- **`initRemote()` already has everything the bridge needs, persisted but unused.** `writeRemoteSettingsLocal` stores `mcp_url`, `observe_url`, `token`, and (bundle path) `fingerprint` into `.claude/settings.local.json` under `unimatrix.remote` (`init.js:217-264`). The bridge can read its config from there, or `init` can pass it as `.mcp.json` args/env. The dead value is `mcp_url`; wiring it is the whole job.
- **`mcp_url` is the server-composed Streamable-HTTP MCP endpoint.** The `v:2` bundle (entry #5081, ADR-002 vnc-038) carries `mcp_url = {public_base}/v1/{slug}` and `observe_url = {public_base}/v1/{slug}/observe`, both `https://`, strict-schema validated by `decodeBundle` (`bundle.js:67-156`). `mcp_url` is the MCP endpoint; `observe_url` is the hook-telemetry endpoint. The bridge targets `mcp_url`; the hook client already targets `observe_url`.
- **The cert-pin machinery is already built and reusable.** `cert-pin.js` provides `computeFingerprint`, `verifyPeerFingerprint` (manual leaf-fingerprint check on `secureConnect` with `rejectUnauthorized:false`), and `applyCertPin`. `transport-http.js` shows the exact safe pattern: complete the self-signed handshake, verify the leaf fingerprint on `secureConnect`, and **only flush the token-bearing body after the pin matches** — destroying the socket on mismatch before the bearer is ever written (`transport-http.js:150-176`). The bridge MUST reuse this pattern so the token never reaches a mismatched/MITM server.
- **The "house pattern" is a raw byte/JSON forwarder (entry #1897, #2582).** Claude Code's `.mcp.json` supports `stdio` (command/args), `sse`, and `streamable-http`. Daemon-backed MCP uses a thin stdio bridge spawned per session. The local Rust daemon's UDS MCP socket uses **newline-delimited JSON** (identical to stdio framing), and its bridge is a raw byte forwarder (#2582). The remote analogue is not a pure byte forwarder — it must translate stdio JSON-RPC ⇄ Streamable-HTTP (HTTP request/response + `Mcp-Session-Id` header + possible `text/event-stream` framing), but the architectural shape (thin per-session stdio process) is the same.
- **Streamable-HTTP session semantics (entry #4708, #4706).** The MCP `initialize` handshake establishes a session; rmcp keys the session on `clientInfo.name` and returns a session id. The bridge must capture the `Mcp-Session-Id` from the `initialize` response and replay it on every subsequent request, and handle both `application/json` and `text/event-stream` (SSE) response framing per the Streamable-HTTP spec. This is the main novel surface area; ass-080 (#777) budgeted it at ~260 of the ~450 bridge LoC and made it the residual delivery risk / flip-bar (see Resolved Decisions, OQ-1).
- **`.gitignore` does NOT cover the creds file (confirmed).** Repo `.gitignore` covers `.claude/worktrees/` and `.claude/scheduled_tasks.lock` only. `git check-ignore` on `.claude/settings.local.json` → not ignored. `gitignoreWarning` (`init.js:273-297`) only warns; #776 wants it fixed on write.
- **File-mode remote observe is BROKEN today (current break, not latent).** `writeRemoteSettingsLocal` writes `unimatrix.remote.{mcp_url, observe_url, token, fingerprint}` (`init.js:230-240`), but the hook client's file-mode `resolve()` reads `unimatrix.remote.{url, token, timeouts}` (`config.js:298-306`): it looks for `url` (never written) and **never reads `fingerprint`**, so `config.pinnedFp` is never populated. The file-mode remote observe path therefore fails its own guards and **silently falls through to local UDS** — remote observe does **not** actually run over HTTPS today, and would run **unpinned** if the `url`/`observe_url` key mismatch were the only thing fixed. Scope B's relocation rewrites exactly this load/store pair, so reconciling the schema (read `observe_url`+`fingerprint`, populate `config.pinnedFp`) and proving remote observe runs over pinned HTTPS post-fix is **in the blast radius of Scope B by necessity**, not an optional extra. (See AC-08d.)
- **Zero-dependency posture is a hard architectural fact.** `package.json` has no `dependencies`, only `optionalDependencies` (platform binaries). The bridge inherits the stdlib-only constraint of the hook client.

## Proposed Approach

High-level, for the design phase to refine (not lock here):

**Scope A — MCP bridge (main; #774 merged — live validation now available):**

*Estimated build surface (ass-080 #777, ~450 LoC net-new across five areas):*
- **stdio framing** — newline-delimited JSON-RPC on stdin/stdout — ~80 LoC
- **HTTP request + `Mcp-Session-Id` capture/replay** — ~120 LoC
- **SSE (`text/event-stream`) parser** — ~90 LoC
- **json / SSE response dispatch** — ~80 LoC
- **MCP lifecycle** (`initialize` → session → `tools/list`, `tools/call`) — ~80 LoC

**TLS / cert-pinning is REUSED from `cert-pin.js` + the `transport-http.js` pinned-flush pattern at ~0 net LoC** — it is *not* counted in the ~450-LoC budget; the gated TLS requirement carries over for free.

1. **New pure-JS bridge module** (e.g. `lib/hook-client/mcp-bridge.js` or a peer), invoked as a stdio process. It reads newline-delimited JSON-RPC on stdin, holds a pinned HTTPS connection to `mcp_url` (reusing `cert-pin.js` / the `transport-http.js` pinned-flush pattern), forwards `Authorization: Bearer <token>`, POSTs each JSON-RPC message to `mcp_url` verbatim, captures and replays `Mcp-Session-Id`, parses `application/json` **and** `text/event-stream` responses, and writes JSON-RPC responses to stdout. Fail-loud on cert mismatch (the bridge is interactive-ish — a broken pin should surface, not silently degrade).
2. **A new bridge entrypoint: `unimatrix mcp-bridge` subcommand, routed to JS in `bin/unimatrix.js` (RESOLVED, OQ-4).** `.mcp.json` invokes `unimatrix mcp-bridge`, routed to the JS bridge in `bin/unimatrix.js` (NOT the Rust binary). This routing is **REQUIRED, not merely preferred**: every non-`init` subcommand today `execFileSync`s the Rust platform binary (`bin/unimatrix.js:36-54`), which a non-Linux / remote-only pure-JS client does **not** have installed — so a bridge subcommand that fell through to the Rust exec path would throw on exactly the clients that need the bridge. The bridge subcommand MUST be routed to JS alongside `init`.
3. **`initRemote()` writes the stdio `.mcp.json` entry** (a remote analogue of `writeMcpJson`), wiring the bridge command + the `mcp_url`/token/`fp` config (via args, env, or by reading `unimatrix.remote`), replacing the "Skipped .mcp.json" line. Idempotent, merge-preserving, dry-run aware.
4. **Bundle-only for cloud MCP (RESOLVED, OQ-2 → option c).** The bridge serves **only** the bundle (`v:2`) path. The legacy `--remote`/`--token` path — which has **no** `fp` pin (#773) — does **not** get the bridge. An unpinned MCP bridge would write the bearer token over an unverified TLS connection (a security regression), and vnc-038's principle was "keep legacy working, don't extend it" — adding MCP to legacy *is* extending it. `initRemote()` on the legacy path emits a **loud, deterministic** unsupported message (not a silent skip). This resolves #773 in the **deprecate-env-HTTPS-for-cloud-attach** direction.

**Scope B — Relocate the credential out of the repo working tree (folded #776; INDEPENDENT, lands FIRST by risk/independence):**
5. **`init` writes the credential to a unimatrix-owned, out-of-tree, per-`projectHash` creds store — never to the repo (OQ-6 resolved).** Replace `writeRemoteSettingsLocal`'s in-tree `.claude/settings.local.json` write with a write to the **existing** per-project dir `~/.unimatrix/<projectHash>/` (mode 0600) — e.g. `~/.unimatrix/<projectHash>/remote.json` holding `{token, fp, mcp_url, observe_url}`. Keyed by **`projectHash`** (`sha256(projectRoot)[:16]`), **not** slug: the slug is server-authoritative and never derived client-side, so a client consumer cannot resolve a slug-keyed store, whereas the hook client already keys per-project state on `projectHash` under `~/.unimatrix/<projectHash>/` (the UDS socket + state dir, `config.js`). (Exact filename is a minor design detail; the **`projectHash`-keyed, out-of-tree, colocated-in-the-existing-per-project-dir** constraint is fixed.) `gitignoreWarning` is removed — with no in-repo creds file there is nothing to warn about.
6. **Both consumers read from the new store.** The relocation must serve **both** the new MCP bridge (which needs `mcp_url`/token/`fp`) **and** the existing hook/observe client (which today reads `unimatrix.remote.{url,token,timeouts}` from `.claude/settings.local.json`, `config.js:276-306`). The hook client's `resolve()` file-mode branch must be repointed at the out-of-tree store (keyed by `projectHash`), reconciling the schema so it reads `observe_url`+`fingerprint` (not `url`) and populates `config.pinnedFp` so remote observe runs over pinned HTTPS (the current-break fix, AC-08d), while preserving its env-var-pair override and UDS fall-through. The bridge reads `mcp_url`/token/`fp` from the same store at spawn time — **token never on the command line, never in `.mcp.json`** (resolves OQ-3). `.mcp.json` references only the bridge command + the project path, never the token.
7. **Migration of any legacy in-tree creds.** If a prior `init` already left a `.claude/settings.local.json` carrying `unimatrix.remote`, decide (design-phase, minor) whether to migrate it into the new store and/or clean the in-tree copy. This is a residual cleanup question, not a headline.

Rationale: the bridge is the minimal, house-pattern-consistent way to deliver the `context_*` surface over a self-signed-pinned HTTPS connection without asking Claude Code to trust an unpinnable cert. Keeping it pure-JS-stdlib honors the single-edge-language and zero-dependency constraints. Posting `mcp_url` verbatim keeps the dumb-client invariant (vnc-038 spine) intact on the new surface. Scope B removes the leak **at its root** — the credential is unimatrix's data and belongs in a unimatrix-owned location, not in Claude Code's settings file inside the repo tree; with the secret out-of-tree there is no commit vector to defend. **Sequencing: Scope B lands FIRST by risk and independence** — it is a low-effort, independent fix that closes a *current live leak* (a single `git add -A` commits a live credential today). Scope A is now live-validatable (#774 merged, PR #778) and is no longer gated; it simply carries more surface area (the bridge + live cloud validation), so B-first is a risk-ordering call, not a blocked-by-A wait.

## Acceptance Criteria

- **AC-01:** After `init --bundle <bundle>`, `.mcp.json` contains a `unimatrix` **stdio** MCP server entry whose command invokes the JS bridge (not the Rust binary), configured against the bundle's `mcp_url`/token/`fp`. The prior "Skipped .mcp.json: remote mode does not register a local MCP server" behavior is gone for the remote path.
- **AC-02:** The bridge is pure Node stdlib — it adds **no** runtime `dependencies` to `package.json` and pulls in no MCP SDK. This is a **decision** (ass-080 #777 BUILD/DIY verdict), not a default posture.
- **AC-03:** Given a Streamable-HTTP MCP endpoint, the bridge proxies a full MCP lifecycle: an `initialize` request over stdin yields a valid `initialize` result on stdout; the bridge captures the session id and replays it; a subsequent `tools/list` returns the `context_*` tools; a `context_search`/`context_get` `tools/call` round-trips. (Validated against a stub/local Streamable-HTTP endpoint as a fast first tier, **and live against the real cloud** — #774 merged (PR #778), so the real cloud is now reachable through the host gate.)
- **AC-04:** The bridge owns its TLS and pins `fp` via the `cert-pin.js` pattern: the bearer token is written to the wire **only after** the leaf fingerprint matches; on mismatch the socket is destroyed before the token is sent and the bridge fails loud with a diagnosable (expected-vs-presented) message.
- **AC-05:** The bridge posts to `mcp_url` **verbatim** — it composes no path, derives no slug, and appends nothing after bundle validation (dumb-client invariant, vnc-038).
- **AC-06:** The bridge handles both `application/json` and `text/event-stream` (SSE) Streamable-HTTP response framing and surfaces the JSON-RPC result on stdout for each.
- **AC-07:** The remote `.mcp.json` write is idempotent and merge-preserving (re-running `init` does not duplicate or clobber other servers), and honors `--dry-run`, mirroring the local `writeMcpJson` contract.
- **AC-08 (#776):** After remote `init`, the bearer token is written **only** to the unimatrix-owned out-of-tree creds store (`~/.unimatrix/<projectHash>/remote.json`, mode 0600), keyed by `projectHash` — and **not** to any path inside the repo working tree. `git status` / `git add -A` in the project surfaces **no** token-bearing file (the credential is not in the tree to be staged), and no `unimatrix.remote` credential is written to `.claude/settings.local.json`. (`.claude/settings.json` hooks are unaffected.)
- **AC-08b (#776):** The store holds **per-`projectHash`** entries: attaching two different projects yields two distinct `~/.unimatrix/<projectHash>/remote.json` files, not two in-repo files; re-running `init` for a project updates that project's entry idempotently without clobbering other projects'.
- **AC-08c (#776):** Both consumers resolve the credential from the new store: the hook/observe client's file-mode `resolve()` (`config.js`) loads token + `observe_url` (+ `fp`/timeouts) for the project's `projectHash` from the out-of-tree store and POSTs to `observe_url` unchanged; the MCP bridge loads `mcp_url`/token/`fp` from the same store. Relocating the credential breaks neither consumer.
- **AC-08d (#776, current-break fix):** After the Scope B relocation, **file-mode remote observe actually runs over pinned HTTPS** — not merely that `config.pinnedFp` is populated. With a `v:2`-attached project, a hook event in file mode resolves `observe_url`+`fp` from the out-of-tree store, populates `config.pinnedFp`, and POSTs the observe event over a fingerprint-pinned HTTPS connection to `observe_url` (verified e.g. against the stub/pinned-endpoint harness), **without** falling through to local UDS. (Regression-proof: pre-fix, the `url`/`fingerprint` schema mismatch silently dropped this path to UDS and would have run unpinned.)
- **AC-09 (#776):** The bearer token never appears in `printSummary()` output, stdout, stderr, the `.mcp.json` (it is read by the bridge from the out-of-tree store at spawn time, never passed on the command line or written into `.mcp.json`), or any other log on the remote path (NFR-06 parity with the bundle path).
- **AC-10:** The legacy `--remote`/`--token` path is **explicitly UNSUPPORTED for cloud MCP** (OQ-2 resolved → bundle-only). On the legacy path, `init` does **not** wire the bridge and emits a **loud, deterministic** message stating cloud MCP requires a `v:2` bundle (the unpinned legacy path is a security regression and is not extended) — **not a silent skip**. The bundle `--bundle` path is the sole cloud-MCP path. (Resolves #773 via deprecation of env-HTTPS for cloud-attach MCP.)
- **AC-11:** Scope B (credential relocation) lands independently of Scope A and carries no #774 dependency — it is validatable without a reachable cloud (write the store on `init`, assert nothing token-bearing lands in the repo tree, assert both consumers resolve from the store).
- **AC-12 (session/attribution stability):** The bridge sends a **stable** `Mcp-Session-Id` and a **stable** `clientInfo.name` for a given attached project — the same identity across bridge restarts/sessions, derived deterministically (e.g. from the project identity / `projectHash`), not randomized per process. The server keys audit attribution on these (vnc-014 / #4708); an unstable identity would bleed attribution across sessions and undercut the 1-client:1-project integrity basis. Verified: two successive bridge spawns for the same project present the same `clientInfo.name` (and replay a stable, not freshly-randomized, session identity) to the endpoint.
- **AC-13 (entrypoint routed to JS):** The `unimatrix mcp-bridge` subcommand is routed to the JS bridge in `bin/unimatrix.js` and does **not** `execFileSync` the Rust platform binary — invoking it on a host with no Rust binary installed (non-Linux / remote-only) runs the bridge rather than throwing on a missing binary (OQ-4 resolved).

## Constraints

- **Single edge language — pure JS.** The client is JS/TS only; the bridge MUST be pure JS. The Rust binary is the Linux-only server and cannot be the client bridge. No Python, no third edge language.
- **Zero runtime dependencies.** The package ships no `dependencies`; the hook client is Node-stdlib-only (`http`, `https`, `net`, `crypto`). The bridge inherits this — stdlib only.
- **Dumb-client invariant (vnc-038 spine).** The server is the sole authority on route shape. The bridge posts to `mcp_url` verbatim — composes no path, derives no slug. `mcp_url` comes from the validated `v:2` bundle (entry #5081).
- **Cert-pin trust model (vnc-038 ADR-002 / F1 finding).** Trust is fingerprint pinning, not CA-trust. The bridge MUST complete the self-signed handshake (`rejectUnauthorized:false`), verify the leaf fingerprint manually on `secureConnect` (`verifyPeerFingerprint`), and flush the token-bearing body **only after** the pin matches — reusing `cert-pin.js`, never re-implementing TLS trust.
- **NFR-06 — no token to logs.** The bearer must not appear on stdout/stderr or in any written-and-loggable surface on the remote path (parity with the bundle decode path, which already keeps the token out of every thrown message).
- **Cloud MCP is bundle-only (OQ-2 resolved → option c, #773).** The bridge serves only the `v:2` bundle path (which carries `fp`). The legacy `--remote`/`--token` path is **not** bridged — it has no `fp` pin, so an MCP bridge would write the bearer over an unverified TLS connection (security regression), and adding MCP to legacy violates vnc-038's "keep legacy working, don't extend it." Legacy cloud-MCP is unsupported with a loud, deterministic message; #773 resolved by deprecating env-HTTPS for cloud-attach.
- **#774 merged (PR #778) — live validation available; bridge must be validated live against the cloud in delivery.** rmcp now wires `allowed_hosts` from `UNIMATRIX_PUBLIC_URL` (PR #778, commit 913b78cb, 2026-06-18), so remote MCP requests no longer 403 at the host gate. The Scope A bridge MUST be validated **live** against the cloud during delivery — not only against a stub. Stub/local-endpoint validation remains a fast first tier (it requires no reachable cloud), but live end-to-end validation is now expected.
- **Streamable-HTTP session contract.** The bridge must honor the MCP Streamable-HTTP transport: `Mcp-Session-Id` capture/replay (entry #4708), and SSE (`text/event-stream`) response framing per spec.
- **Stable session/attribution identity.** The bridge MUST present a **stable** `Mcp-Session-Id` and `clientInfo.name` for a given attached project — derived deterministically (e.g. from project identity / `projectHash`), consistent across bridge restarts, not randomized per process. The server keys audit attribution on these (vnc-014 / #4708); an unstable identity bleeds attribution across sessions and undercuts the 1-client:1-project integrity basis. (See AC-12.)
- **Test infrastructure is cumulative.** Extend the existing hook-client test harness (the Layer-2 real-server harness, `test/`, entry #4835's JS-only CI) and reuse the cert-pin/transport fixtures; do not scaffold isolated test infrastructure. Rust validation is the protocol gates + release workflows, not GH CI (which is JS-client-only).
- **Claude Code `.mcp.json` transport types** are `stdio` / `sse` / `streamable-http` (entry #1897). The chosen wiring is `stdio` (invoking the bridge) precisely so Claude Code does no TLS itself.
- **Credential is out-of-tree and unimatrix-owned (Scope B).** The token-bearing creds store lives under `~/.unimatrix/<projectHash>/` (mode 0600), **never** in the repo working tree, and **never** in Claude Code's `.claude/settings.local.json`. `.claude/settings.json` keeps only hooks (Claude Code executes them and must find them in-tree). Cleartext-at-rest is accepted; the constraint is no-cleartext-in-the-repo and no-namespace-squatting.
- **Per-`projectHash` keying (OQ-6 resolved).** The store is keyed by **`projectHash`** (`sha256(projectRoot)[:16]`), **not** slug, colocated in the existing per-project dir — one store per attached project. Basis: `projectHash` is the only key both consumers can derive identically client-side; the slug is server-authoritative (embedded only in `mcp_url`) and never derived client-side, so it cannot index a client-read store. Precedent: the hook client already keys per-project state under `~/.unimatrix/<projectHash>/` (`config.js`).
- **Both consumers, one store.** The MCP bridge (`mcp_url`/token/`fp`) and the existing hook/observe client (`observe_url`/token/`fp`) must both resolve the credential from the new out-of-tree store, keyed by `projectHash`. The hook client's file-mode `resolve()` (`config.js:276-306`) is repointed there — reading `observe_url`+`fingerprint` and populating `config.pinnedFp` (the current-break fix) — preserving its `UNIMATRIX_REMOTE_URL`/`_TOKEN` env override and UDS fall-through.
- **PRE-EXISTING SCHEMA MISMATCH discovered in code — a CURRENT break that must be reconciled, not faithfully ported.** Today `writeRemoteSettingsLocal` writes `unimatrix.remote.{mcp_url, observe_url, token, fingerprint}` (`init.js:230-240`), but the hook client reads `unimatrix.remote.{url, token, timeouts}` (`config.js:298-306`) and **never reads `fingerprint`** (so `config.pinnedFp` is unpopulated). The file-mode observe path therefore silently fails its guards and falls back to UDS — i.e. **file-mode remote observe does not run over HTTPS today, and would run unpinned if it did**. This is a **current break, not a latent one**. The relocation rewrites exactly this load/store pair; the design MUST land a single coherent schema for the new store (the hook client must read `observe_url` + `fingerprint`, not `url`) and prove file-mode remote observe runs over pinned HTTPS post-fix (AC-08d). Fixing it is in the blast radius of Scope B by necessity, not a new goal.

## Resolved Decisions

- **OQ-1 (bridge depth / build-vs-adopt) — RESOLVED by research spike ass-080 (#777): BUILD/DIY.** The build-vs-adopt question is decided: **build a minimal pure-JS Streamable-HTTP bridge on Node stdlib; do NOT adopt an MCP SDK / `mcp-remote`.** ass-080's cert-pin gate found the only client SDK (`@modelcontextprotocol/sdk`) passes pinning *only* via a hand-written `node:https` custom `fetch` — i.e. it gives **zero leverage on the hard part (TLS pinning)** while costing a 91-package / 25 MB / server-laden tree and its recurring server-transport CVE stream. DIY surface is bounded (~450 LoC, see Proposed Approach → Scope A). Zero-dep (AC-02) is kept **by decision, not by default**.
  - **Residual delivery risk + flip-bar.** Delivery risk now concentrates in **SSE parsing + `Mcp-Session-Id` replay correctness — ~260 of the ~450 LoC** (HTTP request + session replay ~120 + SSE parser ~90 + the dispatch portion ~50). **Documented fallback:** a **hybrid** approach (adopt the SDK transport for JSON-RPC/session/SSE plumbing behind our injected custom-fetch) is the fallback **iff** that ~260-LoC correctness surface proves materially harder to build correctly than estimated. This is the one place the BUILD decision could be revisited during delivery — at the cost of importing the full dep tree *and* still hand-writing the custom-fetch + Node→Web `Response` adapter, so the bar to flip is high.
- **OQ-2 (env-HTTPS / legacy `--remote` — in or out, cf. #773) — RESOLVED → option (c): bundle-only.** Cloud MCP is **bundle-only** (`v:2`). The legacy `--remote`/`--token` path (which has **no** `fp` pin, #773) does **not** get the bridge. Rationale: an unpinned MCP bridge would write the bearer token over an unverified TLS connection (a security regression); and vnc-038's principle was "keep legacy working, don't extend it" — adding MCP to legacy *is* extending it. This resolves **#773 via deprecation of env-HTTPS for cloud-attach MCP**. See AC-10 (legacy path emits a loud, deterministic unsupported message — not a silent skip), the corresponding Non-Goal, and Constraints.
- **OQ-3 (bridge config source) — RESOLVED by the Scope B reshape.** The bridge reads `mcp_url`/token/`fp` from the unimatrix-owned **out-of-tree** creds store at spawn time, keyed by `projectHash` (OQ-6) — **token never on the command line, never in `.mcp.json`**. `.mcp.json` carries only the bridge command + the project path. This was the previous "lean (read from `unimatrix.remote`)" answer, now hardened: the source is the new out-of-tree store, not the in-repo `.claude/settings.local.json`, so the committable-`.mcp.json` leak the old framing worried about cannot occur. Store path/layout settled by OQ-6: `~/.unimatrix/<projectHash>/remote.json`.
- **OQ-5 (gitignore append-vs-ignored-path) — COLLAPSED.** Moot under the relocation: there is no in-repo creds file to gitignore, so the append-vs-ignored-path question disappears entirely. Residual minor design question (downgraded, not a headline): if a legacy `.claude/settings.local.json` carrying `unimatrix.remote` exists from a prior `init`, do we migrate it into the new store and/or delete the in-tree copy on the next `init`? (See Scope B step 7.)
- **OQ-4 (bridge entrypoint shape) — RESOLVED → `unimatrix mcp-bridge` subcommand routed to JS in `bin/unimatrix.js`.** `.mcp.json` invokes the `unimatrix mcp-bridge` subcommand, which `bin/unimatrix.js` routes to the JS bridge implementation — **not** the Rust platform binary. This routing is **REQUIRED, not a preference**: every non-`init` subcommand currently `execFileSync`s the Rust binary (`bin/unimatrix.js:36-54`), which a non-Linux / remote-only pure-JS client does **not** have. A bridge subcommand routed to (or falling through to) the Rust exec path would therefore throw on exactly the clients that need the bridge — the cloud/remote-attached, non-Linux case. So the bridge MUST be JS-routed in `bin/unimatrix.js` next to `init`. (The previous "or `node <bridge-path>` direct command" alternative is dropped; the hard basis above settles it.) See AC-01, AC-13, Proposed Approach → Scope A step 2.
- **OQ-6 (creds-store key) — RESOLVED → key by `projectHash`, colocated in the existing `~/.unimatrix/<projectHash>/` per-project dir.** The out-of-tree creds store is keyed by **`projectHash`** (`sha256(projectRoot)[:16]`), **not** by slug, and is colocated inside the **existing** per-project directory `~/.unimatrix/<projectHash>/` (e.g. `remote.json`, mode 0600) — **not** a new XDG slug-keyed global store. Basis: `config.js` already keys all per-project client state on `sha256(projectRoot)[:16]` (the UDS socket + state dir); the **slug is never derived client-side** (it is server-authoritative, embedded only inside `mcp_url`), so a client consumer cannot resolve a slug-keyed store. `projectHash` is the **only** key **both** consumers (the MCP bridge and the hook/observe client) can compute identically and independently. The store therefore lives at `~/.unimatrix/<projectHash>/remote.json` (exact filename a minor design detail), holding `{token, fp, mcp_url, observe_url}`. (This supersedes the earlier "per-slug global store" framing in Scope B step 5/6 and Constraints; the data is still out-of-tree and unimatrix-owned, but keyed by `projectHash`, not slug.) See AC-08, AC-08b, AC-08c, Constraints.
