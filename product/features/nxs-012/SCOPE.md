# Export/Import: Complete Persistent State Coverage

## Problem Statement

The export/import CLI (`unimatrix-server export` / `unimatrix-server import`) currently handles 8 of the 11 persistent-state tables. Three tables are missing from the pipeline:

1. **graph_edges** -- Stores all relationship edges between entries (Supersedes, CoAccess, Informs, Contradicts, Supports, Advances, Motivates, Prerequisite). After an export/import cycle, goal and feature entries arrive without their Advances edges and NLI-inferred edges. Only bootstrap-derivable edges (Supersedes from `entries.supersedes`, CoAccess from `co_access` table) get regenerated by migration; runtime edges (NLI Contradicts/Supports, S1/S2/S8 Informs, Advances, Motivates) are permanently lost.

2. **observations** -- Stores tool-call telemetry per session (hook invocations, tool names, response sizes, topic signals, phase context). After import, the observations table is empty, causing `query_phase_freq_observations` to return nothing. This means phase affinity scoring cold-starts with neutral (1.0) scores, degrading context_briefing ranking quality until sufficient new sessions accumulate.

3. **cycle_events** -- Stores the lifecycle of feature cycles (cycle_start, phase_transition, cycle_stop events with goals and outcomes). After import, `context_cycle_review` and `derive_is_in_progress` cannot reconstruct cycle history. The `goal_embedding` BLOB column also powers goal-cluster affinity scoring.

These gaps were exposed during a workstation rebuild: after export/import, the knowledge graph was structurally intact (entries, tags, co-access pairs) but semantically degraded (no edges, no phase affinity, no cycle history).

## Goals

1. Export all rows from `graph_edges` (excluding no rows -- see rationale in Background Research)
2. Export all rows from `observations`
3. Export all rows from `cycle_events` (excluding `goal_embedding` BLOB -- see rationale)
4. Import all three new table types with the same correctness guarantees as existing tables (parameterized queries, transaction isolation, deterministic ordering)
5. Bump `format_version` from 1 to 2 in the export header
6. Accept `format_version` 1 (legacy, no new tables) and 2 (with new tables) on import
7. Clean new tables during `--force` import (extend `drop_all_data`)
8. Preserve the existing 8-table export/import behavior unchanged -- this is additive
9. Add `--skip-quarantined` flag to the **export** CLI that omits entries with `status = 3` (quarantined) and all rows that reference them: `entry_tags`, `feature_entries`, `co_access`, `graph_edges` (both `source_id` and `target_id` sides). Rationale: when rebuilding a database, there is no reason to carry forward entries already identified as unwanted. By filtering at export time, the export file is a clean snapshot — import remains a simple full-restore with hash integrity preserved. The skip set is a `HashSet<i64>` built by querying quarantined entry IDs before the per-table export pass; every table exporter checks its entry ID references against it.
10. Require a confirmation safeguard when `--skip-quarantined` is used on export. The user must acknowledge that the export will not be an exact duplicate of the source database. Implementation: require `--confirm` flag alongside `--skip-quarantined`, or emit an interactive "are you sure?" prompt. Without confirmation, the export aborts with a clear message explaining why.

## Non-Goals

- **No goal_embedding BLOB export** -- The `goal_embedding` column in `cycle_events` is a bincode-encoded `Vec<f32>` tied to the specific ONNX model version. After import, embeddings are reconstructed by `embed_reconstruct` for entries; goal embeddings should be re-derived by the goal-cluster pipeline on first cycle activity. Exporting model-specific BLOBs creates a fragile coupling. The column is exported as JSON null.
- **No bootstrap_only filtering** -- Initial analysis considered excluding `bootstrap_only=1` edges from export since they can be re-derived by migration. However, migration only runs when `schema_version < CURRENT_SCHEMA_VERSION`, which is false after a same-version export/import. Including all edges is simpler and ensures no edge loss regardless of version alignment. The bootstrap_only flag is preserved as-is.
- **No observations filtering/compaction** -- No date-range or size-limit filtering. Observations are bounded by the retention GC (`gc_observations` in retention.rs), so the exported set is already the retained set. Typical knowledge bases have 5K-50K observation rows (< 5MB in JSONL).
- **No observation_metrics / observation_phase_metrics export** -- These are derived/computed aggregates with FOREIGN KEY cascades. They are recomputed from raw observations by the metrics pipeline. Adding them would create redundant data in the export.
- **No shadow_evaluations / query_log / sessions export** -- These remain operational/ephemeral tables excluded from the export contract, consistent with nan-001/nan-002 design decisions.
- **No merge/append mode** -- Same constraint as nan-002: import is full restore, not merge.
- **No streaming/pagination** -- All three new tables use `fetch_all` like existing tables. Streaming is a future optimization if databases grow beyond available memory.

## Background Research

### Existing Export Pattern (export.rs)

Each table has a dedicated `export_{table}` async function that:
1. Runs a `SELECT ... ORDER BY {pk}` query via `sqlx::query`
2. Maps each row to a `serde_json::Map` with `_table` discriminator as first key
3. Uses `nullable_int` / `nullable_text` helpers for Option columns
4. Calls `write_row` to serialize as a single JSONL line

The `do_export` function calls all 8 table exporters in dependency order within a `BEGIN DEFERRED` snapshot transaction. New tables must be appended after existing ones.

### Existing Import Pattern (import/mod.rs + inserters.rs)

- `format.rs` defines an `ExportRow` tagged enum with `#[serde(tag = "_table")]` dispatch
- `inserters.rs` has one `insert_{table}` function per variant, using parameterized `sqlx::query` on a single `SqliteConnection` within `BEGIN IMMEDIATE`
- `ImportCounts` struct tracks per-table insert counts
- `ingest_rows` matches on `ExportRow` variants and routes to inserters
- `drop_all_data` DELETEs from FK-dependent tables first, then parent tables
- `print_summary` reports all table counts

### graph_edges Schema (10 columns + AUTOINCREMENT id)

```sql
CREATE TABLE graph_edges (
    id             INTEGER PRIMARY KEY AUTOINCREMENT,
    source_id      INTEGER NOT NULL,
    target_id      INTEGER NOT NULL,
    relation_type  TEXT    NOT NULL,
    weight         REAL    NOT NULL DEFAULT 1.0,
    created_at     INTEGER NOT NULL,
    created_by     TEXT    NOT NULL DEFAULT '',
    source         TEXT    NOT NULL DEFAULT '',
    bootstrap_only INTEGER NOT NULL DEFAULT 0,
    metadata       TEXT    DEFAULT NULL,
    UNIQUE(source_id, target_id, relation_type)
);
```

Key observations:
- `source_id` and `target_id` reference entry IDs but have no FOREIGN KEY constraint (no cascade concern)
- `metadata` is nullable TEXT (JSON-in-TEXT for NLI edges)
- `weight` is REAL (f64) -- requires the same `Number::from_f64` NaN-safety as `entries.confidence`
- UNIQUE constraint on (source_id, target_id, relation_type) means import must use plain INSERT (not INSERT OR IGNORE) to detect data corruption
- AUTOINCREMENT id should not be exported -- let SQLite assign new ids on import. The id is not referenced by any other table.

### observations Schema (10 columns + AUTOINCREMENT id)

```sql
CREATE TABLE observations (
    id               INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id       TEXT    NOT NULL,
    ts_millis        INTEGER NOT NULL,
    hook             TEXT    NOT NULL,
    tool             TEXT,
    input            TEXT,
    response_size    INTEGER,
    response_snippet TEXT,
    topic_signal     TEXT,
    phase            TEXT
);
```

Key observations:
- All nullable columns are TEXT or INTEGER -- no REAL columns
- `id` is AUTOINCREMENT, not referenced elsewhere. Export the id to preserve ordering but import with explicit id (like audit_log pattern) to maintain deterministic row identity.
- `input` can be large (full tool input JSON) -- but is bounded by retention GC
- No FOREIGN KEY constraints

### cycle_events Schema (10 columns + AUTOINCREMENT id)

```sql
CREATE TABLE cycle_events (
    id             INTEGER PRIMARY KEY AUTOINCREMENT,
    cycle_id       TEXT    NOT NULL,
    seq            INTEGER NOT NULL,
    event_type     TEXT    NOT NULL,
    phase          TEXT,
    outcome        TEXT,
    next_phase     TEXT,
    timestamp      INTEGER NOT NULL,
    goal           TEXT,
    goal_embedding BLOB
);
```

Key observations:
- `goal_embedding` is BLOB (bincode `Vec<f32>`) -- excluded from export (see Non-Goals)
- `id` is AUTOINCREMENT, not referenced elsewhere
- `goal` is nullable TEXT (only present on cycle_start events)
- No FOREIGN KEY constraints

### Import Ordering Constraint

Entries must be imported before graph_edges (edges reference entry IDs). The existing import order already places entries early. New table export/import order:

1. (existing 8 tables in current order)
2. graph_edges (after entries and co_access)
3. observations (independent, no FK)
4. cycle_events (independent, no FK)

### format_version Bump

Current format_version is 1. Bumping to 2 signals the presence of new table types. Import must:
- Accept version 1: no new tables expected, skip unknown `_table` values gracefully
- Accept version 2: all 11 tables expected
- Reject version 0, 3+: unknown format

### File Size Impact (500-line rule)

- `export.rs` is 1457 lines (mostly tests). Adding 3 export functions adds ~90 lines of production code.
- `format.rs` is 614 lines (mostly tests). Adding 3 row structs + 3 enum variants adds ~50 lines.
- `inserters.rs` is 178 lines. Adding 3 inserter functions adds ~60 lines.
- `import/mod.rs` is 1264 lines (mostly tests). Changes to `ImportCounts`, `ingest_rows`, `drop_all_data`, `print_summary` add ~30 lines.

All files except export.rs are within limits. export.rs already exceeds 500 lines due to its extensive test suite; the 3 new export functions are production code that belongs in the same module. No file split is warranted.

## Proposed Approach

Follow the exact patterns established by nan-001 (export) and nan-002 (import):

1. **format.rs**: Add `GraphEdgeRow`, `ObservationRow`, `CycleEventRow` structs. Add 3 variants to `ExportRow` enum. `CycleEventRow` has `goal_embedding` as `Option<()>` (always null, ignored on deser).

2. **export.rs**: Add `export_graph_edges`, `export_observations`, `export_cycle_events` functions following the existing column-to-JSON mapping pattern. Add calls in `do_export` after existing tables. Bump header `format_version` to 2. `weight` uses `Number::from_f64` with NaN fallback (same as confidence). `metadata` uses `nullable_text`. `goal_embedding` is omitted from the SELECT (or selected and written as null).

3. **inserters.rs**: Add `insert_graph_edge`, `insert_observation`, `insert_cycle_event` functions with parameterized queries.

4. **import/mod.rs**: Extend `ImportCounts` with 3 new fields. Extend `ingest_rows` match arms. Extend `drop_all_data` to DELETE from new tables (before entries for graph_edges). Extend `print_summary`. Update format_version validation to accept 1 or 2. For version 1 imports, new `_table` values simply won't appear.

5. **Tests**: Unit tests in each module following existing patterns. Integration tests for round-trip with new tables.

## Constraints

1. **Schema version 27** -- The current schema is v27. All three tables exist in the DDL. No migration changes needed.
2. **format.rs tagged enum** -- `ExportRow` uses `#[serde(tag = "_table")]`. Adding variants is backward-incompatible for import (old binaries reject unknown `_table` values). This is why format_version must bump to 2 -- old import code rejects format_version 2 with a clear error rather than failing on unknown table names.
3. **500-line file limit** -- export.rs already exceeds this (1457 lines, mostly tests). New production code (~90 lines) is acceptable since it follows the existing module pattern. If tests push it significantly further, consider extracting export tests to a separate file.
4. **Transaction isolation** -- Export uses `BEGIN DEFERRED` (read snapshot). Import uses `BEGIN IMMEDIATE` (write lock). Both patterns must be preserved for new tables.
5. **AUTOINCREMENT id handling** -- `graph_edges.id` is not referenced by other tables and can be omitted from export (SQLite assigns new ids). `observations.id` and `cycle_events.id` should be preserved (they serve as watermarks and ordering keys used by extraction tick and cycle event sequencing).
6. **BLOB column** -- `cycle_events.goal_embedding` is bincode-encoded and model-version-specific. Must be excluded from export to avoid silent model incompatibility after import.
7. **audit_log trigger** -- The append-only trigger on audit_log prevents DELETE. `drop_all_data` already excludes audit_log. New tables have no such triggers.
8. **Backward compatibility** -- Exports from the new binary (format_version 2) cannot be imported by old binaries (they reject format_version != 1). This is acceptable and follows the established pattern.

## Resolved Questions

1. **graph_edges.id: omit.** The id is synthetic, unreferenced, and preserving it adds complexity with zero value. SQLite assigns fresh ids on import. Export 9 columns.

2. **observations.input size: not a concern.** Retention GC bounds the set. 50K rows of tool-call JSON is single-digit MB. No filtering complexity needed.

3. **goal_embedding reconstruction: lazy.** Entry embeddings need immediate reconstruction (HNSW search). Goal embeddings only feed goal-cluster affinity scoring in context_briefing, which gracefully degrades (NULL embedding → pure semantic path). First cycle completion post-import triggers population naturally. No special post-import step.
