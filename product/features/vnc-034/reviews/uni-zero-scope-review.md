## uni-zero product review (advisory — human judgment required)

**Gate**: scope-review | **Stance**: Proceed to design. The problem is right and the timing is right; the umbrella framing is correct. Resolve OQ-C and OQ-D before/early in design, because they determine whether the wave cut is clean — and tighten one boundary risk (the umbrella becoming a design-in-the-SCOPE).

### Vision / roadmap fit

This is the most direct line to goal #4934 (`personal-cloud`) on the board. The goal entry literally names the destination as "one container, one bearer token, one command, serving N projects to N clients over HTTPS" and names the delivery sequence as #726 → #725 → #727. vnc-034 is that sequence, designed as one capability instead of three. That is exactly the move the goal anticipated — the transport/client F1–F4 substrate is shipped, and this is the "substrate → reachable cloud" closing arc.

Roadmap fit is strong and the sequencing against in-flight work is clean:
- The three constituent issues (#725, #726, #727) are all OPEN and all carry `goal:personal-cloud`. Nothing else in flight contends for these seams. #682 (Rust-hook retirement) and #578 (audit retention) are correctly out of this arc and explicitly deferred.
- The umbrella does not invent scope. Every requirement traces to shipped research (ass-060 seven invariants, ass-050 bearer model, ass-068/069 client). The "enterprise extends, never re-architects" contract from #4934 is carried verbatim into the Constraints section (C6, BearerValidator seam, slug-as-isolation, extensible audit schema). This is the right discipline — OSS code holds the enterprise seams without building enterprise.

The umbrella rationale — shared wire contracts (C2 cert-fingerprint especially) drifting if designed per-issue — is legitimate and is the correct reason to consolidate. A fingerprint format mismatch between server `client-bundle` and client `init --remote` is a delivery-time bug that no single-issue scope would catch. Designing C1–C6 once is the value here.

### Approach commentary

**Strengths**
- The C1–C6 contract enumeration is the strongest part of this SCOPE. Pulling the cross-feature interfaces out as first-class, named artifacts is precisely what an umbrella should do. C4's framing — "design the `resolve_store(request) -> Arc<Store>` *interface* up front, build it minimal in Wave 1 returning the one store, populate with ProjectRouter in Wave 2" — is the right answer to the recurring "how do we leave a seam for an undesigned router" question. It avoids both a blind speculative seam and a Wave-2 re-cut.
- The wave cut (W1 = full transport/security/client stack on the simplest topology; W2 = add only the routing dimension to a known-good base) is sound risk sequencing. Validating the entire TLS/bundle/pinning/client path before adding multi-project means the router meets reality, not a guess. The goal entry independently asserts the same ordering ("designed against the validated single-project cloud — not a pre-built blind seam"), so this is aligned, not a fresh bet.
- Security posture is well-bounded: no plaintext-to-client, no unauthenticated published endpoint beyond `GET /health`, no new `/metrics` (the SCOPE correctly catches that the W2-2 prose mentioned metrics aspirationally but the code has none — do not add an unauthenticated one). nan-014 hardening (non-root 65532, distroless, `:ro` shared) preserved. These are real and correctly framed as acceptance criteria.

**Concerns worth weighing**
1. **Umbrella-as-design risk (primary).** This SCOPE is unusually decided — it already fixes the fingerprint format (C2 `sha256:<lowercase-hex>`), the cert paths, the UID contract, the HTTP-enable mechanism, the public-URL knob. Most of these were resolved in the uni-zero session and that is fine as *design defaults*. But the line between "scope" and "design" is thin here, and the design session must be allowed to genuinely revisit a default if the architecture surfaces a reason — not rubber-stamp. Recommend the design treats the "Resolved this session" block as strong defaults with named rationale, not as locked, so the design phase remains a real gate rather than a formatting pass. Flag for the human: confirm you want these pre-resolved, or hold any of them genuinely open.
2. **Distroless first-boot provisioning.** Constraint says the Rust binary does first-boot cert+token generation because the distroless runtime has no shell. That is correct and necessary, but it concentrates real new risk (cert generation, key `0600`, fail-loud on unwritable `/data`) into the binary's startup path with no entrypoint fallback. Worth ensuring the design gives this its own acceptance attention — it is the one place where "graceful degradation" (principle 5) and "fail loud-and-actionable" are in tension and must be reconciled explicitly.
3. **macOS/Windows client validation is an acceptance claim with no CI substrate named.** The SCOPE asserts the pure-JS client works on Linux/macOS-arm/Windows, but the validation mechanism is unstated. Recommend the design name *how* cross-platform is proven (matrix CI vs. manual attestation) so it is not discovered at delivery. Windows being HTTP-remote-only with no local mode is a sensible cut; just make sure the < 250 KB and "no native binary" gates have a concrete check.

### Recommended answers to open questions

- **OQ-A — bundle wire form (JSON / base64-of-JSON / URL-with-fragment).** Recommend **base64-of-JSON**, single opaque token-like string. Rationale: copy-paste ergonomics (one blob, no whitespace/quoting hazards across a terminal or chat), trivial client parser (decode → JSON), and it reads as a credential so operators treat it like one. Plain JSON invites manual editing and paste-corruption; a URL-with-fragment overloads URL semantics and complicates the `/v1/{slug}` append that C1 says happens at init. Keep the decoded payload JSON so it stays inspectable and forward-extensible.
- **OQ-B — slug discovery for attach.** Recommend **out-of-band for Wave 1** (operator tells the client the slug; no listing surface), and design an **authenticated** `client-bundle --list` / endpoint only if Wave 2 demonstrates a real need. Rationale: any slug-listing surface is new attack surface and a new contract; the cardinality (operator registers, operator attaches) means the operator already knows their slugs. Do not add an unauthenticated listing endpoint under any circumstance — it would violate the "no unauthenticated endpoint beyond /health" acceptance criterion and leak project topology.
- **OQ-C — Wave-1 single-project addressing (`/v1/tools/…` alias vs. mandatory default slug).** Recommend **serve at the `/v1/tools/…` default-project alias** (no slug in Wave 1). Rationale: this is exactly the documented single-project backward-compat behavior (Goal 14, `[[projects]]`-absent ⇒ `/v1/tools/…`), so Wave 2 becomes purely additive — it adds the `/{slug}` dimension without re-pointing any Wave-1 client. Requiring a default slug from day one means every Wave-1 client carries a slug that Wave 2 might re-interpret, and risks the "local path-hash leaking into cloud mode" failure C5 explicitly warns against. The alias keeps Wave 1 clients stable forever. **This is the highest-leverage open question** — it directly decides whether Wave 2 is additive or a migration, which is the whole premise of the wave cut. Resolve it first.
- **OQ-D — wave-to-issue mapping (W1 = #726+#725, W2 = #727).** Recommend **confirm as-is**, with one thing to watch: the SCOPE itself floats carving the C1/C2 connection contract into its own first deliverable consumed by both server and client. I would **not** create a third issue for it — the contract is a design artifact (locked in this design phase), not a separable delivery unit; splitting it adds coordination cost for an interface that both W1 deliverables consume simultaneously anyway. Keep #726+#725 = W1, #727 = W2; express C1/C2 as a design-locked contract section in the brief that both wave deliveries cite. If the architecture genuinely surfaces that the contract needs independent test/release cadence, revisit — but default to not splitting.

### Recommended actions

1. **Proceed to the design session.** The problem is right, the timing is right, the umbrella is justified by the shared-contract drift risk. No reason to hold.
2. **Resolve OQ-C first in design** — it determines whether the wave cut delivers its core promise (Wave 2 additive vs. migration). Recommended: `/v1/tools/…` alias for Wave 1.
3. **Confirm OQ-D as the simple 2-wave / 3-issue mapping** (no separate contract issue) before the brief is written, so issue tracking matches the wave structure from the start.
4. **Have the design phase treat the "Resolved this session" defaults as revisitable-with-rationale, not locked** — preserve design as a real gate. Human: confirm you want C2/cert-path/UID/HTTP-enable pre-fixed, or release any back to open.
5. **Require the design to name three things the SCOPE leaves implicit**: (a) how distroless first-boot cert/token provisioning fails loud and where graceful-degradation applies; (b) the concrete macOS/Windows client validation mechanism and the < 250 KB / no-native-binary check; (c) the slug-discovery decision (OQ-B) and its security justification.
6. **No GH issue created for vnc-034 yet** (per spawn). When created, label `goal:personal-cloud`, reference #725/#726/#727 as the delivery waves, and link goal #4934.
