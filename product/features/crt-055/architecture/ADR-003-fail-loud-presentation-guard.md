## ADR-003: Fail-Loud Presentation Guard — Render "unavailable", Never "0", Per-Metric

### Context
The #750 class (lesson #4998): a metric whose source class is empty renders as `0`, indistinguishable from a measured zero — an honest computation with a dishonest output. ass-077 (RQ-4 stopgap, line 118) recommends a presentation-layer fail-loud guard as the lowest-risk FIRST move: it does not re-ground the retro on any single event class, it just stops lying. The existing `raw_signals_available` flag (`cycle_review_index.rs:80`, `i32`) is a single cycle-wide flag; the new aggregates draw from DIFFERENT source classes (cycle_events, SessionRecord.outcome, query_log ∪ injection_log, the activity fold, compaction_events), so presence must be tracked PER METRIC, not one flag for all (SR-08). "0 of 0" must be distinguishable from "0 of N".

### Decision
Sequence this guard FIRST within the feature (Wave 1; SCOPE Open Q5, SR-03). Extend the presence concept from one cycle-wide `raw_signals_available` to per-metric `available` flags carried on the `RetrospectiveReport` presentation layer: each aggregate's flag is set from whether its source class is non-empty for the cycle (e.g. zero cycle_events → phase metrics "unavailable"; zero compaction_events → `compaction_reread` "unavailable"; undeclared/held-route-miss activity fold → transcript metrics "unavailable"). The formatter renders "unavailable" (with a terse reason) instead of `0` when the flag is false. Ratios are presented from stored numerator/denominator pairs (ADR-004), never a pre-divided single number, so "0 of 0" prints "unavailable" while "0 of N" prints a genuine measured rate. The flags are presentation-only — they do not gate the single writer (ADR-002) and do not change which source a metric reads.

**Binding clause — behavioral signals render COARSE/DIRECTIONAL (human decision, 2026-06-16).** `transcript_error_count`, `transcript_refusal_count`, and `signal_class_counts_json` are derived from **unvalidated regex matches against content-opaque deltas** — the counts cannot be audited post-hoc (no content is retained to re-verify a match). The num/den discipline and the per-metric presence flag above help, but they do not make a regex count *precise*. Presentation MUST mark these counts directional, not exact: render them with a coarse/directional qualifier — e.g. a leading `~` (`~3 refusals`) or an explicit "directional" / "approx." label — visibly distinguishing them from **exactly-counted** aggregates (phase counts, phase transitions, session ratios, compaction count), which render bare. This is a presentation-honesty rule, a sibling to the "unavailable"-not-"0" rule: both stop the report from implying a precision it does not have. The qualifier is presentation-only; the stored integer counts are unchanged, and the coarse marking is orthogonal to the `available` flag (a directional count can still be "unavailable" when its fold is missing).

### Consequences
Easier: the believable-zero misread is stopped before any column lands; the guard is decoupled, low-risk, and ships first; per-metric granularity correctly distinguishes "compaction never happened" from "transcript fold missing." The coarse/directional marking gives a second, distinct honesty signal — a consumer can tell a regex-derived behavioral count (auditable: no) from an exactly-counted aggregate (auditable: yes) at a glance, so no one over-trusts the refusal/error numbers. Harder: every new metric must carry its presence flag and the formatter must branch on it; "unavailable" copy must be precise enough to be actionable, not alarming; the formatter now carries a second axis (exact vs directional) and the catalog of which counts are regex-derived must stay correct as classes are added (all `signal_class_counts_json` entries are directional by construction).
